# Astimate: Specification

**Status:** draft v0.5, 2026-09-27. Supersedes v0.2, which framed the tool as a pre-work planning signal. This revision makes the post-implementation quality gate the primary use and keeps planning and ranking as secondary uses.

Astimate is a static-analysis tool that checks whether an LLM-written change left a package in a state a human or the next agent can maintain. It extracts structural metrics per package, compares them against a baseline and a set of thresholds, and fails when the package got worse. It also produces a **rebuild estimate**: how many agent passes, and roughly how many human days, a from-scratch rebuild of the package would take. That is the microservices "rewritable in two weeks" bar, restated for packages and agents, and it drives ranking and planning. It runs as a CLI, a CI step, a Claude Code hook and a Model Context Protocol (MCP) server. Go is the first supported language; everything downstream of metric extraction is language-agnostic.

Sections 8 through 11 (gate, CLI, MCP, calibration) and 14 (milestones) are written to be split directly into stories.

---

## 1. Goals

1. **Gate:** fail a change that makes a package materially less manageable, and say exactly which rule was broken so the agent can fix it without human interpretation.
2. **Ratchet, not absolute:** judge a change against the package's own baseline, so work on legacy packages is not blocked by pre-existing debt while new debt is.
3. **Self-check loop:** let an agent run the gate itself before declaring work done, via CLI, hook or MCP.
4. **Rank and plan:** estimate rebuild effort for every package in a module so humans and agents can see which packages have outgrown the rebuildable bar and where debt is concentrated.
5. **Honest defaults:** the gate thresholds are calibrated against a reference corpus (section 11.1); the rebuild estimate is labelled as coming from uncalibrated parameters until the rebuild experiments of section 11.2 have run.

## 2. Non-goals

- Not a linter for individual findings. Astimate reports package-level structure, not line-level style.
- Not a human-effort estimator. `scc` already does COCOMO.
- Not a code-health product with proprietary scoring. CodeScene covers that space; Astimate is free, local and targets LLM failure modes specifically.
- No network calls in the default path.
- No auto-fixing. The gate reports; the agent or human changes the code.

## 3. Definitions

| Term | Meaning |
| --- | --- |
| Module | A Go module rooted at a `go.mod`. The unit of analysis for fan-in and "internal". |
| Package | A Go package directory within the module. The unit that gets metrics, a score and gate verdicts. |
| Internal import | An import whose path is inside the module path from `go.mod`. |
| Fan-out | Number of distinct internal packages this package imports. |
| Fan-in | Number of distinct internal packages that import this package. |
| Baseline | The raw metrics of a package at a reference point: a git ref (usually the merge-base with the default branch) or a committed baseline file. |
| Threshold | A per-metric limit: an absolute `max`, a `max_delta` versus the baseline, or both. |
| Violation | A metric that exceeds a threshold at head. Any violation fails the gate. |
| Raw metrics | The language-agnostic struct in section 6 that an extractor produces. |
| Rebuild estimate | Estimated agent passes and human days to rebuild the package from its tests and exported contract, computed from raw metrics and the rebuild parameters in config. |

## 4. What the gate targets (evidence summary)

The gate targets the ways LLM-written changes tend to degrade a package. The metric set and default thresholds follow from that, with the rebuild estimate's evidence kept for ranking.

The Strength column is measured, not cited: each gated rule's precision (the share of the commits it fired on that a reviewer labelled `block`) and recall (the share of `block` commits it fired on) on the hand-labelled agent commits of the 2026-10-14 validation (15 `block` and 137 `allow` commits from five repositories, capacity-only labels set aside; 8.2 and 11.4), and whether the rule fails or warns there. With 15 `block` commits one commit moves recall by 6.7 points, so the column ranks the rules rather than measuring them finely. The Evidence column keeps what the literature says.

| Failure mode | Metric(s) | Evidence | Strength |
| --- | --- | --- | --- |
| Copy-paste instead of extraction | `duplication_pct`, `dup_blocks` | Industry reports on AI-assisted repositories (GitClear, 2024 and 2025) show rising duplicated blocks and falling moved-or-refactored code. Not peer-reviewed, but consistent across years. | The strongest measured: `dup_blocks` precision 55.6%, recall 66.7%, and, with every rule failing, the only rule that fails `block` commits no other rule does (2 of 15; with the four warn rules of 8.2, `dup_blocks_cross_pkg` alone fails one more); `duplication_pct` 50.0% and 13.3%, all of them also `dup_blocks` commits |
| Package bloat past what the next agent can hold | `tokens_est`, `sloc`, `largest_file_sloc` | Successful agent trajectories typically stay under 20 to 30k tokens, and single-shot resolve rates collapse at 64k tokens of context (arXiv 2602.16069); long context remains a weakness for every model tested (arXiv 2505.07897); failed agent trajectories are consistently longer than successful ones (arXiv 2511.00197). | Strong: precision 100% for all three (no `allow` commit failed), recall `sloc` 33.3%, `tokens_est` 20.0%, `largest_file_sloc` 13.3% |
| Exporting everything | `exported_symbols` | No direct study. Wider API surface raises fan-in cost and the facts the next agent must hold (Coherence Debt, arXiv 2608.16630). | Strong as measured: precision 100%, recall 26.7% |
| Untested additions | `untested_exports`, `has_tests` | Agents self-correct through a run-and-check loop; a package without tests denies the next agent that loop. | Weak as a failing rule: `untested_exports` precision 29.2%, recall 46.7%, over the false-failure budget and with no `block` commit only it catches, so it warns; `has_tests` 100% and 6.7% |
| Hidden mutable state | `globals`, `init_funcs` | No direct study. Plausible; kept at low weight. `globals` counts only variables the package can change: sentinel errors, embedded files, build information set by the linker, compiled regexps and read-only tables hold no state and are left out (6.5). | Unproven: `globals` precision 16.7%, recall 6.7%, so it warns; `init_funcs` never fired |
| Coupling shape | `instability`, `abstractness`, `main_sequence_distance` | Martin's package metrics are widely reported but their validation as predictors is mixed and none exists for Go, whose consumer-defined interfaces invert the abstract-provider assumption. Reported only until the corpus measurement in 11.1 shows where good Go modules sit. | Unproven |
| Deep nesting | `max_nesting`, `cognitive_p90`, `changed_func_cognitive_max` | Classical complexity metrics show no consistent correlation with LLM performance (arXiv 2602.07882). Kept as a gate on regressions only. | Weak: `max_nesting` precision 50.0%, recall 6.7%; `changed_func_cognitive_max` 100% and 6.7%; `cognitive_p90` fired on no `block` commit, so it warns |
| Coupling growth | `internal_imports` | Failures come from coupled facts absent from context (arXiv 2608.16630; CrossCodeEval, arXiv 2310.11248). | Unmeasured: fired on no `block` commit and one `allow` commit, so it warns |
| Blast radius | `fan_in` | No direct study; blast-radius reasoning: a change to a package with many importers can break each of them. Reported for ranking (`rank --sort fan_in`) and recorded in the rebuild estimate's contract detail; it enters neither the estimate formula (7.2) nor the default gate. | Unproven; reported for ranking |

**Extractor interface** (language-agnostic):

```go
type Extractor interface {
    Language() string
    Detect(root string) bool
    Packages(root string) ([]string, error)
    // Extract computes raw metrics for one package. The module context is a
    // pointer so the extractor can fill its cache slot on first use.
    Extract(ctx context.Context, mod *ModuleContext, pkg string) (RawMetrics, error)
}
```

**Testing pattern.** The contract is defined once in `internal/metrics` and verified once by a conformance suite in `internal/metrics/metricstest`, an importable non-test package in the style of `testing/fstest`. It exports `TestExtractor(t, ext, fixture)`, which checks detection, package listing, validation, determinism, error handling, cross-package invariants (the module-wide sum of `fan_in` equals the sum of `internal_imports`; `has_tests` is true whenever `test_funcs` is above 0) and golden comparison against `testdata/<lang>/fixture/golden/*.json`. Every language extractor's own tests call it once; language-specific unit tests (import path rules, statement kinds, tokenizer normalization) stay in the nested package. `metricstest` also exports a fake extractor built from a map of `RawMetrics`, so the estimate, gate and CLI can be tested without loading a real module. `Packages` returns the language's native package identifier (Go: the full import path); golden files are named by that identifier with the module path prefix removed, so `example.com/fixture/a` is `golden/a.json` and the root package is `golden/root.json`.

When an extractor also implements the optional `ModuleMetrics`, the suite checks the module row: it validates, its v0 fields are 0 and its v1 fields null except the module-wide ones, it is deterministic and honours cancellation, the per-package sum of `dup_blocks_cross_pkg` is between twice the row's value and the row's value times the package count, and it matches `golden/module.json`. The fake takes a module row through `WithModuleRow`. An extractor may also implement the optional `ModuleDetailer`, whose `ModuleDetails` names every cross-package block of the module row (package, file relative to the module root, line range); `Details` lists the blocks touching a package. When `Details` returns `CrossBlocks`, the suite requires exactly `dup_blocks_cross_pkg` of them, each with at least two occurrences in at least two packages that `Packages` lists (the package itself among them), with slash-separated relative files and line ranges where 1 <= start <= end; when the extractor is a `ModuleDetailer`, `ModuleDetails` must name exactly the module row's `dup_blocks_cross_pkg` blocks, each listed in the `Details` of every package it touches; recorded `UntestedPositions` and `GlobalPositions` must number one per untested export and one per global; the fake takes module details through `WithModuleDetails`. An extractor implementing the optional `ImporterLister` has its `Importers` checked: sorted, distinct, excluding the package itself, exactly `fan_in` entries, unknown package rejected.

### 6.1 Token estimation

Default: `tokens_est = bytes / chars_per_token`, `chars_per_token` defaulting to **3.2**. Tokenizers differ, and the default targets the Anthropic tokenizer family, since Claude Code is the first gate consumer: published measurements put code at about 2.7 characters per token on the tokenizer introduced with Opus 4.7 and about 3.7 on the one before it, so 3.2 is a middle estimate for a Claude session. OpenAI's `o200k_base` is sparser: measured on this repository's Go source it runs about 3.75 to 4.0 bytes per token for non-test code and about 2.7 to 3.3 for test code. The original spec's 4.0 therefore happens to be close for o200k and undercounts for Claude by roughly 20 percent. The ratio is a config value so it can be set per target model.

Opt-in exact counting: `--tokenizer=o200k` via `pkoukk/tiktoken-go`, offline, exact for that tokenizer only. There is no offline Anthropic tokenizer; the Anthropic count-tokens API is not called by default because it is a network dependency.

### 6.2 Test-file handling

Test files are excluded from every metric except `tokens_est_with_tests`, `test_files`, `test_funcs` and the reference side of `untested_exports`. External test packages (`foo_test`) in the same directory fold into the package.

### 6.3 Duplication

Tokens are taken from `go/scanner` over non-test files. Identifiers, literals and comments are normalized (identifier to `ID`, string and numeric literals to `LIT`) so renamed copies still match. The automatic semicolons that `go/scanner` inserts at line ends are dropped from the stream, so a repeat never extends onto a neighbouring declaration's line. A duplicate block is a maximal token sequence of length at least `duplication.min_tokens` that occurs at least twice, found with a suffix array or rolling hash over the normalized stream. Nested and overlapping repeats are merged: a shorter repeat wholly inside a longer one's occurrences is not counted separately, and occurrences that overlap are unioned before coverage is computed. `dup_blocks` counts distinct maximal sequences after merging; `duplication_pct` is covered SLOC divided by package SLOC times 100, rounded to one decimal, and `duplicated_lines` is that covered SLOC. Generated files are excluded, from the token stream and from the package SLOC denominator alike. A block whose tokens are all literals or the punctuation `, { } : [ ] ( ) ;` is a data table, not code, and is dropped after merging when `duplication.ignore_literal_only` is true, which is the default: measured over 225 standard-library packages it moves the 90th percentile of `duplication_pct` by 0.1 and removes `html` (an entity map at 94%) and `crypto/des` from the top ten while every dropped block inspected was data (see `calibration/notes/duplication-literal-only.md`). With `duplication.fold_signs` true, which is the default, a `+` or `-` that directly precedes a numeric literal and does not follow an operand (an identifier, a literal, `)`, `]` or `}`) counts as part of the literal for that rule, so a table of negative numbers is data too; the sign stays a separate token for matching, so no match is gained or lost. Folding the sign into the normalized stream was rejected: it lets `f(-1)` match `f(1)` and raised `math` from 37.7% to 44.1% (see `calibration/notes/duplication-refinements.md`). The literal-only rule applies to whole blocks after merging; a literal table inside a block that also holds code is counted, because trimming literal edges strips closing braces off code and splitting at short runs cuts code too (see `calibration/notes/duplication-literal-runs.md`). With `duplication.split_literal_runs` true, under the literal-only rule, each block is first cut at every run of at least `duplication.min_tokens` literal-only tokens (a sign counting as literal when `fold_signs` is on); the parts of at least `duplication.min_tokens` tokens between the runs are kept as blocks with every occurrence of their block, and parts with the same first occurrence and length count once. This drops tables that declaration headers join into one block. It is off by default: over std and 36 corpus modules every changed block read was data and the only code uncovered was fragments below `min_tokens`, but it moves `duplication_pct` in 43 of 1039 corpus packages and the thresholds were fitted without it (see `calibration/notes/duplication-literal-runs-corpus-2026-09-28.md`). The threshold and normalization rules are config values.

Every block, within a package or across packages, is marked by what it is made of, from a shape the extractor gives each token by the syntax around it (6.5): *declarative* (a token inside a composite literal, a struct type or a constant or variable declaration), *idiom* (a token of an error return, a call statement or an assignment of a call), *neutral* (outside every statement: package and import clauses, function headers, the braces of a function body) or *code* (any other statement). The first kind that holds is the block's: **declarative** when no token of any occurrence is idiom or code and at least one is declarative; **idiom** when none is code and at least one is idiom; **self-overlap** when an occurrence starts on or before the last line of the previous occurrence of the same block in the same file, as a run of like calls matching itself a line down does; **code** otherwise, a block of neutral tokens only included. `dup_blocks_code` counts the code blocks of `dup_blocks`; the extractor's details name each block's kind, and each cross-package block of `dup_blocks_cross_pkg` carries one too; the report does not print each block's kind, but a `dup_blocks` finding's suggestion says it counts blocks of any kind and how many are code, and a `dup_blocks_code` finding's cites the first code block, an added one first. An extractor that gives no shapes marks every block code or self-overlap. Measured on the standard library, this repository and the five replays of 2026-10-13 in `calibration/notes/dup-block-kinds-2026-10-14.md`. The default gate judges `dup_blocks`, blocks of every kind: a `dup_blocks_code` rule in its place lowered J on the hand labels of 2026-10-14 (8.2, `calibration/notes/dup-blocks-code-2026-10-14.md`).

### 6.4 Untested exports

An exported function or method counts as untested when no identifier in any test file of any package of the module (internal or external test package) resolves, via `types.Info.Uses`, to that function or to a method with the same name on the same receiver type. The module is loaded once, so the references of every test file of every package are collected in one pass, keyed by the referenced object's package, and shared by every package measured in the load, like the reverse import graph; a constructor exercised only by another package's tests is tested, and a test-support package whose exports only other packages' tests use reads as tested (rule d below also counts the package's own non-test code). Exported types, vars and consts are not counted; the metric targets behavior, not declarations. Reported as a count and, in the gate, primarily as a delta so new untested behavior fails while legacy gaps are only reported.

A method the runtime or the standard library calls without a test naming it is covered when its receiver type, or a pointer to it, implements (`types.Implements`) an interface of this closed list that declares that method: `error`, `fmt.Stringer`, `fmt.Formatter`, `fmt.GoStringer`, `encoding.TextMarshaler`, `encoding.TextUnmarshaler`, `encoding.BinaryMarshaler`, `encoding.BinaryUnmarshaler`, `json.Marshaler`, `json.Unmarshaler`, `sort.Interface`, `io.Reader`, `io.Writer`, `io.Closer`, `io.ReaderFrom`, `io.WriterTo`, `http.Handler`, `driver.Valuer`, `sql.Scanner`, `flag.Value`, `http.Flusher`, `http.Hijacker`, `http.Pusher`, `pflag.Value` (`String`, `Set`, `Type`), `pflag.SliceValue` (`Append`, `Replace`, `GetSlice`), `slog.LogValuer`, `heap.Interface`; and the method-set conventions the `errors` package calls without an interface: `Unwrap() error`, `Unwrap() []error`, `Is(error) bool` and `As(any) bool`, each treated as a one-method interface. The list is closed: a method whose type does not implement the listed interface still counts, so an `Error` with another signature, or `Len` on a type without `Less` and `Swap`, is counted. A generic receiver is checked as the method declares it, with its own type parameters.

Further refinements. A declaration whose doc comment contains the line `//astimate:untested` (optionally followed by a reason) is excluded from the count and listed separately, for intentionally untested wrappers. A method called in a test through an interface value counts as referenced when the concrete receiver type, or a pointer to it, implements that interface and has a method of that name; the interface may come from any package, and the call may be in a test file of any package of the module whose test binary holds the receiver's package, that is, whose type-check imports it directly or through other packages of the module. A generic receiver type is checked through each instantiation of it that appears in the calling test package's test files; an instantiation that a test never names or holds is not seen. A selection inside a generic function declared in a test file is checked once per instantiation of that function in the test files, with its type arguments substituted into the receiver type. A method of a generic type declared in a test file is checked the same way, once per instantiation of that type in the test files, and a generic function or type instantiated inside another with that one's type parameters takes each of the enclosing one's instantiations, substituted, through chains of up to eight. A generic test type that appears only as a field type of another generic test type is not carried through; that is a known gap. These interface-dispatch and generic rules apply to the test files of every package of the module alike.

Four further rules settle exports no test names and are each listed separately in the details, like the directive (`option_funcs`, `interface_methods`, `test_support`), so what they removed stays visible:

- **(a) Option funcs.** A func or method whose body is the single statement `return func(o *T) { ... }`, where the literal has a parameter, no result, and consists of nothing but assignments to fields of that parameter (`o.timeout = d`, `o.tags = append(o.tags, t...)`), is the functional-option idiom and is left out of the count when no test refers to it. A literal that validates, branches, returns a value or calls a method is more than a setter and still counts.
- **(b) Interface methods of unexported types.** An exported method of an unexported receiver type is left out when no test refers to it and the receiver, or a pointer to it, implements a named interface declared in a package of the module that declares that method, and some test file of any package of the module holds a value of that interface (the interface is the type of an expression there) in a test binary that sees the receiver's package. The type is reachable from outside its package only through such an interface, so whatever test drives the interface exercises it. This differs from the dispatch rule above, which needs a test to call the method itself; here any use of the interface is enough. Interfaces from outside the module are covered only by the closed list.
- **(c) `pflag.Value` and `pflag.SliceValue`** are on the closed list, matched by method set because the package need not be imported by the module.
- **(d) Test-support packages.** A package that some other package's test files refer to and that no other package of the module imports from a non-test file is a test-support package: its code runs only under tests. A reference from its own non-test files to its own funcs and methods, a direct use or a call through an interface, counts as a test reference, so the fakes and helpers of `metricstest` that its suite calls read as tested. References from such code to other packages count for nothing. The package's exports are listed under `test_support` when only this rule settled them.

Rules a and b apply only to exports no test refers to, and a method that reaches the count through (a) or (b) is not a reference: it does not make `has_tests` true.

Measured on the standard library (381 packages, 8,216 counted exports), this repository and the four corpus modules loadable offline, the refinements before rules a to d cover 14.4%, 2.8% and 3 to 21% of counted exports respectively (`calibration/notes/untested-exports-refinements-2026-09-29.md`). Rules a to d remove a further 182 (2.2%) of the standard library's exports (option funcs 1, interface methods 105, test support 69, with overlap), 5 of this repository's 441 (1.1%), and 10 of 68 in `BurntSushi/toml` (14.7%, one test-harness package) and 6 of 224 in `google/go-cmp` (2.7%), none in `google/uuid` or `pelletier/go-toml/v2` (`calibration/notes/untested-exports-refinements-2026-10-13.md`). The gate rule is `max_delta: 0` with no `max`, so no threshold changes.

**Coverage.** With `--coverage` (or `coverage: true` on an MCP tool) the static rules above are complemented by what the tests actually ran, for the exports no test names: behaviour reached through an HTTP handler or a connect client, through goldens that drive a whole pipeline, through a CLI test binary, or through an interface no test holds. Each test run of the invocation (section 6, `coverage_pct`) uses `-coverpkg=./...` and writes a profile; the profiles of the runs that passed are merged, a block counting as run when any run executed it. For a selected package with untested exports, the tests of every module package whose test binary links it, through any chain of module imports, also run, a directory holding only test files included; their own coverage is not reported. An export counted by `untested_exports` whose body, from its opening to its closing brace, holds a block of at least one statement that ran is tested, and `untested_exports_covered` is the count of the rest. It is null for a package that no passing run linked, such as one without test files that no other package's tests reach: there the profile says nothing and the static count stands. The exports the run settled are recorded with the package's details, and a check cites the exports no test ran first. The run executes the module's tests, so it is off by default like `coverage_pct`; on goKMS `internal/kms`, whose 45 counted exports are all exercised by an end-to-end suite in a test-only directory, it leaves 8; `internal/auth` goes from 6 to 0 and mark's `confluence` from 27 to 20 (`calibration/notes/coverage-untested-2026-10-14.md`).

**Skipped packages.** A package skipped because it does not load (6.5) has no type information, so its test files are read syntactically, by name, as TypeScript reads (13.1): in such a file, a selector `pkg.Name` whose `pkg` is the name an import of the file gives a loaded package of the module, or a bare identifier `Name` in a file that dot-imports one (the file's own declarations aside), refers to the exported func `Name` of that package; any other selector `x.Name`, `x` not the name of an import (an unnamed import outside the module is known by names guessed from its path: the last element, the one before a major version such as `v2`, and that element less a `.vN` suffix, a `go-` prefix or a `-go` suffix), refers to every exported method `Name`, on any receiver, of each loaded package the file imports. Shadowing and receiver types are not checked, so these references may over-count; they count as another package's test references, for `untested_exports` and `has_tests` alike, and the skipped package's non-test imports count against rule d below as any package's do.

TypeScript reads the same module-wide index by name (13.1). Its test files include those of a directory with no non-test source file, such as a top-level `test/`: that directory is no package and has no row, but what its files name counts as tested.

### 6.5 Counting rules

Rules that the section 6 table leaves implicit, fixed here so goldens and implementations agree (`testdata/go/fixture/golden/COUNTING.md` shows each applied):

- `globals` counts names, not specs or blocks: `var a, b = 1, 2` is 2; `_` is excluded.
- `globals` counts mutable state only. A package-level var spec is left out, all its names together, when no name of it is written in the package and it is one of five idioms that hold none: (a) a sentinel error, every name of type `error` and every initializer a call to `errors.New` or `fmt.Errorf` whose arguments are all constant expressions (`var ErrBad = fmt.Errorf("bad: %d", 3)`; `fmt.Errorf("x: %w", base)` counts); (b) an embedded file, a spec carrying a `//go:embed` directive; (c) build information, every name of a boolean, numeric or string basic type (not a named type such as `type Level int`) and every initializer constant or absent, as for a value set by `-ldflags -X`; (d) a compiled pattern, every name a `*regexp.Regexp` initialized by `regexp.MustCompile` or `regexp.MustCompilePOSIX` of constant arguments; (e) a read-only table, every name a map, slice or array (named types included) initialized by a non-empty composite literal whose keys and elements are constants, compiled patterns or nested literals of the same kind, so a table of function values, pointers (`[]*T{{...}}` included) or other variables still counts, and which no code of the package could mutate: an element assigned, incremented or assigned by `range` (`table[k] = v`, `table[k]++`), the table or a part of it passed to `append`, `delete`, `clear`, `copy`, a function of `maps`, `slices` or `sort`, a function or method of the package, or a call the type information does not resolve, or used as the receiver of such a method. Reading it in an expression, a `range`, an index read, `len`, `cap` or passing it to another package's function does not. The scan for (e) reads every authored non-test file once, on the first table it meets. A name is written when a function body or package-level var initializer of the package's authored non-test files assigns it (`=`, an assignment operator or a `range` with `=`), increments or decrements it, or takes its address; test files, generated files and other packages are not read, so a test hook assigned only from a test, or an exported variable set by an importer, stays excluded. Everything else counts: maps, slices, channels, pointers, structs, `sync` values, `regexp.MustCompile` results, `flag` variables, function values, and any variable written anywhere in the package. The decision uses `go/types`: an identifier resolves to a package-level variable through `types.Info`, so a local that shadows a global is not a write of it. For a cgo package, whose source trees the type information does not cover, the package scope still types each name, calls resolve through the file's imports, constants are recognized syntactically (literals, named constants and operators over them), and every assigned identifier with a global's name counts as a write, which can only count more. The scan for writes rides the one walk of each function body that measures its nesting and fingerprints it. Measured on the standard library and this repository in `calibration/notes/globals-mutable-state-2026-09-29.md` and, for (d) and (e), `calibration/notes/globals-readonly-tables-2026-10-13.md`. The Go implementation lives in `internal/lang/golang/internal/inspect/globals`, which `inspect` wraps.
- `has_tests` (Go) is true when the package has a test function of its own or when a `_test.go` file of any package of the module references one of its exported funcs or methods, by the same reference index `untested_exports` reads (6.4; a method counted only by the closed interface list is not a reference). `test_files` and `test_funcs` stay the package's own. A package whose exports only other packages' tests use, a test-support package, therefore reads as tested and the `has_tests` requirement does not fire on it. The rebuild estimate's `has_tests` input is this value. TypeScript follows the same rule with its name-matched index (13.1): a package some test file of the module names an export of has tests.
- `role` says what a package is for in its module, the first of these that holds: **`main`**, a composition root, which nothing can import (Go: a package named `main`; TypeScript: a package whose directory holds a file a `bin` entry of the root `package.json` names, a string or an object of strings, or a package that exports nothing); **`generated-only`**, a package with non-test files every one of which is generated (Go; TypeScript has no generated-file rule); **`test-support`**, a package only tests use, as rule d of 6.4 defines it (some other package's test file refers to it and no package of the module imports it from a non-test file; Go only); **`library`**, any other. The names live in `internal/metrics/role`. A threshold's `roles` (8.1) is matched against it. The module row has none, and a row recorded without one, by an extractor that records none or before roles existed (a baseline file, a replay row), is judged as a `library`. A `bin` entry that names build output, such as `./dist/cli.mjs`, names no package, so such a command's source package is `main` only when it exports nothing.
- `func_count`, `cognitive_total`, `cognitive_p90`, `cyclomatic_total` and `cyclomatic_p90` include `init()` functions.
- `cognitive_p90` and `cyclomatic_p90` are the nearest-rank 90th percentile over per-function values, by the same code; a package with no functions reports 0.
- Cyclomatic complexity is McCabe's count as gocyclo computes it, per top-level function or method over the same functions as cognitive complexity: 1, plus 1 for each `if`, `for` and `range` statement, each `case` clause of a `switch` or type switch and each `case` of a `select` (not `default`; a case listing several values counts once), and each `&&` and `||` operator; a func literal counts in the function that contains it, and `else` adds nothing. TypeScript counts the same over the nodes its cognitive walk visits (13.1). It is reported, not gated: no rule in the default configuration, since a gate rule needs a measurement against the hand labels first (11.4); gocyclo enforces it per function. It counts each decision once wherever it sits, so unlike cognitive complexity it does not weigh nesting or breaks in linear flow (`else`, labelled jumps, runs of mixed boolean operators). Each function's cognitive and cyclomatic complexity is listed in the report's `details.functions` (10.2) and recorded in a baseline file's function records (8.3). On this repository it equals gocyclo's on every function and its Spearman correlation with cognitive complexity is 0.96 (`calibration/notes/cyclomatic-2026-10-14.md`).
- `uses_cgo`, `uses_reflect` and `generated_files` are read from the source files' import specs and headers, never from files cgo generates; blank and renamed imports of `reflect` or `unsafe` count.
- Generated files: a non-test file with a line matching `^// Code generated .* DO NOT EDIT\.$` before the package clause (`ast.IsGenerated`) counts in `files`, `generated_files` and `tokens_est_generated`, and is still read for `internal_imports`, `external_imports`, `stdlib_imports`, `fan_in`, `fan_in_tests`, `uses_cgo` and `uses_reflect`, since generated code imports real packages. It is left out of every size and structure metric: `sloc`, `largest_file_sloc`, `tokens_est`, `tokens_est_with_tests`, `func_count`, `cognitive_total`, `cognitive_p90`, `cyclomatic_total`, `cyclomatic_p90`, `max_nesting`, `globals`, `init_funcs`, `exported_symbols`, `abstractness`, `untested_exports` (a generated export needs no test), `dup_blocks` and `duplication_pct` (the stream and the `sloc` denominator alike), and the function list behind `changed_func_cognitive_max`. A rebuild reruns the generator rather than writing its output, so the section 7 estimate, unchanged in formula, leaves the generated volume out. A generated `_test.go` file is a test file and still counts in `tokens_est_with_tests`. For a cgo package the rule reads the source files, never the files cgo writes, which cgo marks as generated.
- `internal_imports`, `external_imports`, `stdlib_imports`, `fan_in` and `fan_in_tests` count the distinct packages that the import specs of source files resolve to, keyed by package path. A blank (`_`) or dot (`.`) import counts like any other. An import that only files cgo generates hold (such as `runtime/cgo`) counts in no class, so every internal edge counts once in `fan_in` and once in `internal_imports`, and their module-wide sums are equal.
- `abstractness` counts an exported type as an interface when its underlying type is an interface, so a definition or alias naming one (`type R io.Reader`, `type R = io.Reader`) counts.
- `instability`, `abstractness` and `main_sequence_distance` are rounded to three decimals; `main_sequence_distance` is computed from the unrounded ratios.
- `changed_func_cognitive_max` diffs functions, never the package: a head function is matched to a baseline function of the same package by receiver base type (pointer, type parameters and parentheses stripped; empty for a plain function) and name, as a multiset so repeated names such as `init` pair up. A matched function is modified when its fingerprint differs. The fingerprint is a hash of the body's syntax tree with identifiers normalized to `ID` and literals to `LIT` as in 6.3; comments and positions are not in it, so comment, layout and gofmt edits, variable renames and literal values do not mark a function changed, while any change to operators or control flow does. A direct call to the function's own name is kept distinct, since cognitive complexity scores recursion. A renamed function or a method moved to another receiver is new; a deleted function is not changed; every function of a package new at head is changed. `init` functions count.
- `tokens_est` sums bytes across files first, then divides by `chars_per_token` and truncates.
- Embed patterns: a package whose `//go:embed` pattern matches no file (the directory is gitignored build output, present in the working tree and absent from a baseline checkout) loads and is counted as usual, because no metric reads embedded files. Each such package is reported once on stderr at warn level, naming the package and the pattern. An embed error is a warning, never a skip. The warning is not carried in the JSON row or the replay, which already records load errors per commit.
- Packages that do not load: a module package whose own files or test files fail to load (a module it imports is not in the module cache, a file does not parse or type-check, cgo cannot build it) is skipped, with its test variants, and every other package is loaded and counted as usual, so one broken package does not cost the module its gate. A skipped package has a reason, `missing module`, `syntax error`, `type error` or `build error` (`missing module` whenever one of its errors names a module that is not available, else by the kind of its first error), with ` in test files` appended when only its test files fail, and its first error. It is not listed by `Packages`, so `rank` leaves it out and `assess` on it fails naming the reason; each is reported on stderr at warn level, once per load, and once per `check` (the baseline load of a check logs only the skips head did not). The import graph keeps its edges, so the `fan_in` and `fan_in_tests` of the packages it imports, and the `internal_imports` of those importing it, are what they would be had it loaded; its test references and duplicate blocks still count for its neighbours, read from its files without type information: the references of its test files syntactically (6.4), and its non-test files in the cross-package duplication stream (6.3), so a block between it and a loaded package counts in that package's `dup_blocks_cross_pkg` and on the module row, while it has no row of its own. A non-test file of it that does not parse adds no blocks, and a test file that does not parse is read as far as it parses. A module none of whose packages loads fails with the first package's error, and a build cache go list cannot write still fails the whole load. `check` lists every skipped package (8.5) and exits 2 only when one of them is among the packages it would judge (section 9).
- Token shapes for the block kinds of 6.3 (Go): spans read from the file's syntax tree, a token taking the innermost one. A composite literal, a struct type and a `const` or `var` declaration (package level or local) are declarative; a function declaration or literal is neutral, so its header and braces are and its statements take their own shapes, which resets a function literal inside a literal or an idiom. An idiom statement is idiom with everything in it: an `if` with no `else` whose condition is an identifier `!= nil` and whose body is one `return`, its init, if any, an assignment of a call; an expression statement that is a call; an `=` or `:=` whose every right side is a call, a composite literal or its address. In a file `main.go` of package `main` a call statement is declarative instead, the registration calls of a command's scaffolding. Any other statement is code, its nested statements shaped on their own; block, labeled, empty and declaration statements add no span. When the bytes read differ in length from the parsed file, no shape is given and the file's blocks are code.
- Token shapes (TypeScript), from node kinds: an object or array literal, an interface, type alias or enum declaration and a class field are declarative; a `const`, `let` or `var` declaration is declarative when every value is absent, a literal, an object or array literal or a function, idiom when every value is one of those or a call (`await` and `new` included) and one is a call, code otherwise; a function, arrow function, method or class body is neutral; an expression statement that is a call or an assignment of a call or of an object or array literal, and an `if` with no `else` whose body is one `return` or `throw` (the guard clause that is TypeScript's error return) are idiom, everything in them included; any other statement is code; block, import, export and empty statements open no shape.
- `fan_in_tests` counts other packages whose test files import this package; a package's own external test package importing it does not count.
- `sloc` counts a line with code and a trailing comment as code.
- For a cgo package, every syntactic metric is counted from the package's Go source files, never from the files cgo generates; `import "C"` is not an import of any class. The type-dependent `untested_exports` uses the type-checked trees, whose declarations and doc comments match the source.

### 6.6 Churn

`churn_commits` and `churn_authors` say how often a package changes, from the history of the repository holding the module, read at its HEAD with one `git log --first-parent --diff-merges=first-parent --no-renames --relative --name-only -n <churn.commits> HEAD` per run, run in the module root so paths come relative to it and files outside the module are not listed. Each listed file is attributed as changed-package detection attributes it (8.4): the extractor's source classifier names its package by module-relative directory, and a file counts when it makes its directory a package and is not a test (a Go `_test.go` file; a TypeScript test or declaration file is a member, not package source, so it does not count). A Go file whose version in the measured tree has a generated-code header (6.5) is left out; a file no longer in the tree counts, having no header to read. A commit counts once per package it touched, whatever the number of files; a merge counts the files it changed against its first parent, so the commits of a merged branch count once, as the merge, under the merge's author. Renames are not followed, so a commit that moved a file counts for the package it left and the one it entered, and an earlier commit that touched the file under its old name counts for the old package, which is the truth of the history. The engine reads the history once per operation and fills every package it reports: `assess`, `rank`, the head rows of `check`, `baseline write` (as of the commit the file records) and, through the engine, the MCP tools, each replayed commit of `dryrun` and the calibration replay (from that commit's own history, so a row's churn is what the tool reported at that commit) and the corpus rows of `calibration/collect`. The baseline block of a `check` against a git ref carries none, and against a baseline file what the file recorded; no rule reads either. Outside a git repository, before the first commit, in a shallow clone (whose oldest commit would list every file as added, such as a CI checkout at depth 1 or the depth-1 corpus clones of `calibration/collect`), or where git cannot run, both metrics are null; `assess` prints them as `n/a` and `rank` as `-`. Measured on this repository on 2026-10-14, the walk takes 0.04 s at the default window, and `dryrun --last 10` took 34.6 s with churn on against 31.2 s off, a difference inside the spread between runs of one setting on a shared host (`calibration/notes/churn-2026-10-14.md`). Churn enters neither the rebuild estimate nor the tier: `rank --sort churn` orders by it, and a package high on both `agent_passes` and `churn_commits` is the one to split first.

## 7. Rebuild estimate

The estimate answers one question: if this package were deleted and rebuilt from its tests and exported contract, how much work is that? It is secondary to the gate and drives `rank`, `assess` and the summary line of `check` once calibrated (8.5). It has units, so it can be measured (section 11.2) and argued with.

### 7.1 Inputs

A rebuild must reproduce a contract and pass a spec, and the raw metrics describe both:

| Input | From | Role |
| --- | --- | --- |
| Essential volume | `tokens_est * (1 - duplication_pct / 100)` | Code that must be written; duplicates collapse in a rebuild |
| Spec | `tokens_est_with_tests - tokens_est`, `test_funcs` | Tests are the executable specification the rebuild is checked against |
| Contract | `exported_symbols` | Signatures that must survive. `fan_in` is recorded in the term's detail, not in the formula (7.2) |
| Unspecified behavior | `untested_exports`, scaled by `coverage_pct` when measured | Behavior that must be reverse-engineered from the old implementation |
| Hidden contract | `globals`, `init_funcs` | State and ordering that no signature reveals |

### 7.2 Agent estimate

Everything a rebuild needs must fit in context at once, or the work is partitioned and pays coordination overhead. With `B` the context budget (default 37,500 tokens, fitted in 11.2; the earlier 25,000 was the knee in the evidence):

```
rebuild_tokens = essential_volume
               + spec_tokens
               + exported_symbols * tokens_per_export            (default 0, fitted)
               + untested_exports * tokens_per_untested_export * (1 - coverage_pct / 100)   (default 300, fitted)
               + (globals + init_funcs) * tokens_per_hidden_state (default 0, fitted)

r            = rebuild_tokens / B
agent_passes = r                       when r <= 1
             = r ^ superlinear_exponent when r > 1     (default 1, fitted: past the knee the measured cost grows no faster than r)
```

`agent_passes` is reported to one decimal. Below 1.0 the package is rebuildable in one pass with room to spare. The coverage factor applies only when `coverage_pct` is non-null (`--coverage`); without it the term is the full step penalty of `tokens_per_untested_export` per untested export, as in the worked example. The unspecified driver's detail then records `coverage_pct`, and its suggestion says what coverage scaled the term to. `human_days` (7.3) does not read coverage. In `check`, the baseline has no coverage, so the summary's baseline `agent_passes` is estimated with head's `coverage_pct`.

Worked example (the reference test reproduces every value to four decimals) under the placeholder parameters of `configs/uncalibrated.yaml` (40, 800, 400, exponent 1.3), which keep every term visible: `sloc` 1200, `tokens_est` 10000, `tokens_est_with_tests` 16000, `duplication_pct` 20, `exported_symbols` 30, `untested_exports` 15, `globals` 2, `init_funcs` 1.

```
volume      = 10000 * 0.8          =  8000
spec        = 16000 - 10000        =  6000
contract    = 30 * 40              =  1200
unspecified = 15 * 800             = 12000
hidden      = (2 + 1) * 400        =  1200
rebuild_tokens                     = 28400
r           = 28400 / 25000        = 1.136
agent_passes = 1.136 ^ 1.3         = 1.1803   (reported as 1.2)
```

Under the shipped defaults (0, 300, 0, 1, budget 37,500) the same package is volume 8000 + spec 6000 + contract 0 + unspecified 4500 + hidden 0 = 18500 tokens, r = 0.4933, `agent_passes` 0.4933 (reported as 0.5).

Note that `duplication_pct` also lowers `human_days` through 7.3; "halves the volume term and nothing else" in the tests refers to the five token terms.

### 7.3 Human estimate

A rough figure using published COCOMO basic organic-mode coefficients, the same model `scc` uses, with unspecified behavior inflating the effective size:

```
kloc_eff   = (sloc * (1 - duplication_pct / 100) / 1000) * (1 + 0.5 * untested_ratio)
person_months = 2.4 * kloc_eff ^ 1.05
human_days = person_months * days_per_month   (default 19)
```

where `untested_ratio = untested_exports / max(exported_symbols, 1)`, clamped to [0, 1]. Labelled as an estimate in every output. For the worked example above: `untested_ratio` 0.5, `kloc_eff` = 0.96 × 1.25 = 1.2, `person_months` = 2.4 × 1.2^1.05 = 2.9064, `human_days` = 55.2211.

### 7.4 Tiers, drivers and suggestions

| Tier | `agent_passes` | Meaning |
| --- | --- | --- |
| ONE_PASS | <= 1.0 | Rebuilt in 97% of measured runs (65 of 67, 11.2). This is the bar. |
| FEW_PASSES | 1.0 to 3.0 | Rebuilt in 78% of measured runs (14 of 18); plan the split |
| PARTITION | > 3.0 | Unmeasured: no corpus package scores over 3.0 under the fitted parameters; split before any large change |

A pass is a unit of the estimate, not a context window: the fit found one estimate token corresponds to about 7.6 tokens of session footprint (11.2). The rates are from 85 Claude Code (Opus) rebuilds of 31 packages; the 14 whole-tree rebuilds passed 12 times.

`drivers` lists the two largest non-zero terms of `rebuild_tokens` (volume, spec, contract, unspecified, hidden). `suggestions` are generated from drivers whose term is at least 10% of `rebuild_tokens`, with the metric values, for example "7 exported functions have no test (Parse, Encode, Decode, Flush, Close and 2 more); a rebuild would have to reverse-engineer their behavior". At most five names are listed. Gate violations and warnings always carry a suggestion from the same per-metric templates.

All parameters live in the `rebuild:` section of the config. The shipped default carries the parameters fitted by section 11.2 on 2026-09-28 (`rebuild-2026-09-28-claude-code-opus`) under the gate retune's version `thresholds-2026-10-14b`, so the text report labels the estimate line `(estimate from calibrated parameters)` and the JSON report carries `rebuild.calibrated: true`; a config whose version neither starts with `rebuild-` nor is a `thresholds-<date>` dated after that fit (10.2) is labelled `(estimate from uncalibrated parameters)` with `calibrated: false`; the label describes the estimate only, never the gate thresholds, which section 11.1 calibrates independently.

### 7.5 Acceptance invariants

- Go stdlib `errors` is ONE_PASS; `net/http` is PARTITION.
- A package with zero fan-in, tests present, no duplication and under 5k tokens is ONE_PASS.
- Monotonicity: increasing `tokens_est`, `exported_symbols`, `untested_exports`, `globals` or `init_funcs` never lowers `agent_passes`; increasing `duplication_pct` alone never raises it; raising `coverage_pct`, or measuring it where it was null, never raises it; adding test tokens raises only the `spec` term (on the worked example under the placeholder parameters, 1,000 more test tokens move `agent_passes` from 1.1803 to 1.2346; under the shipped defaults from 0.493 to 0.52), and adding tests never raises `human_days`.

## 8. Quality gate

### 8.1 Semantics

`astimate check` evaluates every changed package (or all packages with `--all`) against a thresholds config. Thresholds fall into two kinds, and the distinction is what separates "got worse" from "got more features".

**Density rules** measure how the code is written, independent of how much there is. Adding features should never raise them, so they are gated on the change itself with `max_delta`: the largest permitted increase from baseline to head, usually 0. A feature written without copy-paste adds no duplicate blocks; ten new exports with tests leave `untested_exports` unchanged. Negative values require improvement. A density rule may also carry a `max`, but it is a ceiling on what a change may introduce, not a retroactive judgment: it is evaluated for a package with no baseline, and for a package whose value crossed it (below the `max` at baseline, above it at head). A package already at or over the `max` at baseline is judged by the rule's `max_delta` alone, so an unchanged or improved legacy value above the `max` passes, and so does a rise within `max_delta`: a package at `cognitive_p90` 43 against the default `max` 20 passes at 45 and fails at 47 on `max_delta +3`, and one at 80% duplication is not failed for that history, only for a rise of more than `max_delta`. Without this every small rise of a legacy value failed on the `max` and the rule's `max_delta` was never consulted, which a field evaluation on 2026-10-13 found on packages of CLI flag tables. A density rule may carry `max` alone when its metric is already a change against the baseline (`changed_func_cognitive_max`); it is evaluated whenever the metric is non-null at head, and with no `max_delta` to fall back on, its `max` fails a value over it that is new or rose. `ratchet_from_zero` requires `max_delta`.

**Floors and direction.** A density rule may carry a `floor`, a finite number: a head value at or below it fails neither the rule's `max_delta` nor its `max`, however much it rose, since the package is nowhere near what the rule guards. It is valid on density rules only, and takes precedence over the `max`, so a useful floor is below it. Two density metrics are a ratio and a percentile, which also rise when code is only deleted, so against a baseline their rule is judged only when the change raised what they measure: `duplication_pct` only when `duplicated_lines` (6.3) rose, so a share that rises because SLOC fell under the same blocks passes; and `cognitive_p90` only when a function changed since the baseline (6.5, the set `changed_func_cognitive_max` is taken over) is more complex than the baseline's `cognitive_p90`, which is when `changed_func_cognitive_max` at head is above it, so a p90 that rises because simple functions were deleted passes. When either value is missing (a baseline file written before `duplicated_lines` existed, a check without a function-level diff, a replayed row without either) the rule is judged as before. A package with no baseline is judged against the `max` only, as below. A field evaluation on 2026-10-13 found zero-delta rules failing trivial values, `max_nesting` 1 to 2 and `cognitive_p90` 1 to 8 in a package of three functions, where the p90 is its most complex function, and ratio rules failing deletions, `duplication_pct` 26.8 to 34.1 under the same six blocks as SLOC fell from 406 to 320 and `cognitive_p90` 3 to 11 as fifteen trivial option functions were deleted: about seven findings were floors and four deletions, and none was a true positive.

**Duplicated lines.** A configuration may gate `duplicated_lines` (6.3), the SLOC a duplicate block covers, as a density rule; with `max_delta: 0` and a `floor` it fails a change that adds a duplicated line to a package past the floor. It catches a copy the block count misses: on 2026-10-13 kubesentry's `internal/output` copied its Text and CSV methods a third time while two blocks merged into one longer one, `dup_blocks` falling 6 to 5 and `duplication_pct` 83.3 to 73.7 as the package grew, and `duplicated_lines` rose 135 to 157. Its finding is located on a duplicate block's occurrence like the other duplication rules' and merges with them (One finding per cause, below). The embedded default leaves it out: over the five replays of 2026-10-14 under the hand labels it added no `block` commit the gate missed and two false failures, small additions to packages long past any floor, lowering the pooled J by 1.4 points at floors 0, 10 and 20 alike (`calibration/notes/duplicated-lines-rule-2026-10-14.md`).

**Changed functions.** `changed_func_cognitive_max` is one number, the worst changed function's complexity, but `check` judges its `max` per function: each changed function (6.5) carries the complexity of the baseline function it was matched to by receiver and name, the first such baseline function, in baseline order, that neither an unchanged head function nor an earlier changed one matched, or none for a new or renamed function. A changed function over the `max` fails when it has no baseline value, when its baseline value was below the `max` (it crossed it), or when it rose by more than the rule's `over_max_delta` (default 0) from a baseline value already at or over the `max`; a function already over the `max` that held, fell or rose by at most `over_max_delta` passes. At the default `max` 50 and `over_max_delta` 5 (8.2), a function at 57 that stays 57 passes, one at 369 that goes to 385 fails, a new function at 60 fails, and one at 48 that rises to 53 fails. The rule reports one finding, on the most complex failing function (the first on ties): its `base` and `head` are that function's (no `base` for a new function), its `limit` is `max <max>`, or `over max by N, allowed M` for growth of a function already over the `max` under a positive `over_max_delta`, and the finding is named and located on that function, so a legacy function that stays over the `max` neither fails the change nor hides a new function that does. Without this a fix inside a 369-complexity function failed every change to it, and judging only the worst function would let a new function at 60 pass beside it. `over_max_delta` is valid on a density rule only for `changed_func_cognitive_max`, and needs `max`. A caller that has no per-function list (the calibration tools re-evaluating rows replayed before 2026-10-13) judges the row's one value as any `max`-only density rule.

**Capacity rules** measure how much code there is. They are supposed to grow with features, so they carry no delta. They have an absolute `max` that answers a different question: has the package outgrown what one agent can hold in context? The fix for a capacity breach is a split, not a smaller feature. Like a density `max`, the ceiling is a violation for a new package, or for a package whose value crossed it (below the `max` at baseline, above it at head); a legacy package already over the ceiling whose value is unchanged or fell gets a warning saying so, not a violation, so identical head and baseline trees never fail the gate. A package already at or over the ceiling at baseline whose value rose is held by a ratchet instead: each capacity rule has an `over_max_delta` (default 0), the largest increase one change may make there. A rise of at most `over_max_delta` is a warning whose `limit` reads `over max by N, allowed M` (N is how far head is over the `max`, M the `over_max_delta`) and whose suggestion names the growth and says to split the package; a larger rise is a violation with the same `limit` and suggestion. Under the default of 0 any rise is a violation with `limit` `max <max>`, as it was before the field existed. Without the ratchet every commit to a package past its ceiling fails until the package is split, which is what drives exemptions and bypasses: in the gate validation (11.4) over 97% of `tokens_est` and `sloc` violations were growth of a package already over the `max`, which no retuned `max` prevents. `over_max_delta` is valid only on a capacity rule and on `changed_func_cognitive_max` (Changed functions, below), and must be a finite number at least 0. Each capacity rule also has a `warn_at` fraction (default 0.75) above which `check` emits a non-failing warning naming the headroom, so a split can be planned before a hard failure lands mid-feature.

**Module row.** A module-level row with package path `<module>` carries module-wide metrics, today `dup_blocks_cross_pkg` as the number of distinct cross-package blocks. It exists because one edit that copies code between packages changes two packages' counts. It is baselined under the id `<module>`, which no Go import path or TypeScript package directory can equal, by `baseline write` and by git baselines alike. A rule whose metric is module-wide (today only `dup_blocks_cross_pkg`) is evaluated on the module row only: package rows still report their own count but are not gated on it, so one cross-package copy is one finding, not one per package it touches. Every other rule is evaluated on package rows only, so the module row, whose v0 metrics are zero, is never judged by a package rule. A baseline file without the row, one written before it existed, skips the module-wide rules for that run with one note on stderr (`baseline file has no module row; module-wide rules skipped; run \`astimate baseline write\` to add it`) and still reports the row's metrics; `baseline write` always writes the row, and a git baseline always has it because it is extracted. A baseline file written before the id was reserved stores the row under `module`; it is read as the module row when the file has no `<module>` key and every v0 field of that row is zero (otherwise it is the package of that import path), with one warning on stderr (`baseline file stores the module row under the old key "module"; run \`astimate baseline write\` to rewrite it`). `check` reports it first whenever at least one package is selected, including a check of named packages: the MCP `check_package` tool gates it too, but for a check of named packages the module-wide rule judges only the cross-package blocks blamed on them: with a git baseline, whose merge-base blocks are recorded, the added head blocks (below: new, those whose set of packages occurs more often at head than at the baseline, at least the floor long and not moved) that touch a named package, counted as an increase over the baseline's value; with a baseline file, which stores only the count, the head count when any head block touches a named package and the baseline's count otherwise. A copy between two other packages therefore neither fails the check nor appears in its findings, while the row still reports the full count; the finding's suggestion names the packages sharing each blamed block. The default gates it with `max_delta: 0` and `max: 450` (8.2), without `ratchet_from_zero`, so a module with no baseline is held to the max rather than counted from zero.

**Added cross-package blocks.** Once a module is over the max, every change that repeats `duplication.min_tokens` normalized tokens between packages would raise the count, and a split of a package would turn the duplicates its halves shared into cross-package ones. So when the baseline records its blocks (a git baseline does; 8.4), the module rule judges not the head count but the baseline's count plus the blocks the change *added*: the head blocks that are new by the set of packages they touch (8.4), that are at least `duplication.min_tokens_cross` normalized tokens long (default 120, at the top of the range where golangci-lint's `dupl` starts reporting copies; a block whose length the extractor does not give is kept), and that were not moved. The matching by package set counts only the blocks that clear the floor on each side, so a short legacy block cannot hide a long copy between the same packages, nor a long legacy block be blamed for a short repeat added beside it, and it reads each package a rename joined (below) as its whole group, so a legacy block a carved-out package took with it from its source, its copy in a third package staying put, matches its baseline self rather than reading as new. A block is moved when every package it touches lies in one group a rename joined (8.4): a package whose row was seeded by a rename and the packages it was seeded from, groups sharing a package being one, so the code a split leaves shared between its halves, or among several packages carved out of one, is not added, while a copy from a carved-out package into an unrelated one is. A change that adds such a block therefore rises over `max_delta: 0`, and one that adds none does not, whatever the head count; the value judged is reported in the finding, and the row reports the full count. The finding names only the added blocks: its suggestion counts them, says they are at least the floor long and cites the first one's first occurrence and its first occurrence in another package, and it is located on that first occurrence. A check of named packages blames those same added blocks, the ones touching a named package, so the CLI and the MCP `check_package` judge a block alike. Against a baseline file, which stores only the count, or an extractor that does not name its blocks, the full count is judged as before and the suggestion ends by saying so (`The baseline records no cross-package blocks, so the whole count is judged rather than the blocks this change added.`). The floor was swept at 40, 60, 80 and 120 on a sample of the replays' duplication failures (`calibration/notes/cross-blocks-added-2026-10-14.md`), then at 60, 80, 100 and 120 on the hand labels of the five replays, whose module rows record the blocks each commit added (11.3): 120 keeps the gate's recall at 86.7% and lowers its false failures from 10.2% to 5.8%, the copies it stops counting being functional-options scaffolds, a block two struct fields split and a block an import alias grew, all `allow` (`calibration/notes/cross-floor-2026-10-14.md`). A declarative block (6.3) every occurrence of which lies in a `main` package (6.5) is counted but never added, on either side of the matching, like a block under the floor: commands repeat flag tables and registration calls by design. The extractor's module details give the role of each package a block touches; without them nothing is exempt. Measured on the five replayed repositories, goKMS and kubesentry at HEAD, no block shared only by commands is declarative today, so the exemption changes no verdict there (`calibration/notes/package-roles-2026-10-14.md`).

Boolean metrics use `require: true` with an optional `when` guard (for example `has_tests` when `sloc > 100`). Requirements, like density `max`, do not fire on an unchanged legacy package: `has_tests` fails a package that lacks tests only when it is new or when its `sloc` grew.

**Roles.** Any rule may carry `roles`, a list of package roles (6.5: `main`, `library`, `test-support`, `generated-only`), each named once; the rule judges only rows of those roles, and a rule without `roles` judges every row. A row whose role the rule leaves out is not evaluated by it at all: no violation, warning or note, as for a metric the row does not compute. A row with no role is a `library`. Several rules may name one metric when their roles differ, as the default's two `has_tests` rules do (8.2); rules whose roles overlap would both judge a row. The filter lives in the gate (`gate.Threshold.Judges`), so `check`, `check_package` and the calibration tools re-evaluating replayed rows apply it alike. A composition root wires every component of a program, so fan-out, surface and the tests a library needs read differently there: in the field evaluation of 2026-10-13 ztp's `cmd/broker` failed `internal_imports` 20 -> 21 on a change that removed a fake from its wiring, and `untested_exports` counted exports nothing can import (`calibration/notes/package-roles-2026-10-14.md`).

**Severity.** Every rule has a `severity`, `fail` (the default) or `warn`. A `warn` rule is evaluated exactly as its kind requires, and what would be a violation is reported as a warning instead, with the violation's fields (`metric`, `base`, `head`, `limit`, `location`, `suggestion`) and `severity: warn`; it never changes `passed` or the exit code. Its other findings, a capacity rule's `warn_at` and over-ceiling warnings, stay ordinary warnings without a severity. The same rule at `fail` produces the identical finding as a violation. `warn` is for a rule worth showing an agent in its self-check loop but not worth bouncing a person's commit: one with positive J that is still over the false-failure budget of 11.4, or one a linter already enforces. The validation report measures a `warn` rule on its own (11.4), so its worth is known before it is promoted to `fail`. The embedded default ships four rules at `warn`, `untested_exports`, `globals`, `cognitive_p90` and `internal_imports` (8.2): on the hand-labelled commits of 2026-10-14 each failed `allow` commits and no `block` commit that another rule did not fail too. Every other rule ships at `fail`.

**Source.** A rule on `untested_exports` may carry `source: coverage`: it then judges `untested_exports_covered` (6.4) when the run measured it, with `--coverage` or `coverage: true` on an MCP tool, and `untested_exports` otherwise, so a hook without `--coverage` behaves as before. Both sides of a comparison are counted alike. Baselines never run tests, so a check estimates the baseline's covered count as its recorded untested exports less those head's run executed, reading an export the change kept as running at the baseline as it runs at head; against a baseline without export names (a baseline file written before they were recorded), the rule judges `untested_exports` on both sides. A package new at head ratchets its covered count from zero. The finding keeps the metric `untested_exports`, carries the covered counts as `base` and `head`, and its limit ends in `on untested_exports_covered`. `source` is accepted only on `untested_exports`, and only `coverage` is a source. The embedded default keeps the rule static, with the option shown commented out, because the run executes code.

**One finding per cause.** After every rule of a row is evaluated, and before a `warn` rule's breach is reported as a warning and before exemptions apply (8.6), findings that report the same change are merged into one, per one table (`internal/gate`'s `mergePairs`, applied in this order): (1) the same rule breaching both its `max_delta` and its `max` is one finding whose `limit` joins both with `and` (`max_delta +6 and max 40`); (2) a `tokens_est` finding merges into a `sloc` finding on the same row; (3) a `dup_blocks_code` finding, in a configuration that gates it beside `dup_blocks`, merges into a `dup_blocks` finding on the same row; (4) a `duplication_pct` finding merges into a `dup_blocks` finding on the same row, whose suggestion already quotes the percentage; (5) a `duplicated_lines` finding merges into a `dup_blocks` finding on the same row; (6) and (7) a `duplication_pct` and a `duplicated_lines` finding that (4) and (5) left merge into a `dup_blocks_code` finding on the same row, the rule a configuration gates in place of `dup_blocks`; (8) a `duplication_pct` finding still left, no block rule having fired, merges into a `duplicated_lines` finding on the same row. The merged finding is attributed to the first rule of its pair (`sloc`, `dup_blocks`, `dup_blocks_code`, `duplicated_lines`), keeps that rule's values, suggestion and location, and its `limit` gains `; ` and the other rule's metric, values and limit (`max 1000; tokens_est 15000 -> 17500, max 16000`, values to two decimals, `head` alone without a baseline value); the other rule's metric is listed in the finding's `also` (10.2), followed by any rule merged into it first. Two rules merge only when their values moved in the same direction from the baseline (a value with no baseline counts as a rise). Only breaches merge, and only two reported the same way: two violations, or two breaches of `warn` rules; a violation never merges with a warn rule's breach, so a merge never changes `passed` or the exit code. A capacity rule's ordinary warnings (`warn_at` and over the ceiling) never merge, since each names its own headroom. Without this one paste was reported as `dup_blocks` and `duplication_pct` with identical suggestions, and one growth as `sloc` and `tokens_est`; a field evaluation on 2026-10-13 found such doubles in about 19 of 148 false findings, and they make every failure read as worse than it is.

Packages that are new at head have no baseline. They face the capacity ceilings and the absolute `max` of every density rule. Delta rules are evaluated against zero only for rules marked `ratchet_from_zero: true`, which are the count-of-things-added metrics (`dup_blocks`, `untested_exports`, `globals`, `init_funcs`): a new package with three untested exports fails, a new package with forty tested exports under the ceiling passes. Intensive metrics such as `max_nesting`, `cognitive_p90` and `duplication_pct` are not ratcheted from zero, since every real package has some nesting; for a new package only their `max` applies.

A package that did not exist at the baseline is new, but one that existed there and could not be analysed is not: when the baseline tree loads but the package fails to load in it (a type or syntax error, a missing module; the packages the extractor skips, 6.5), the baseline has no row for it because its history is unknown, not because it is empty. Such a package is judged against the absolute limits only: the capacity ceilings and the `max` of every density rule apply as they do to a new package, but no rule ratchets from zero and no requirement rule applies (whether it grew is unknown), so the blocks, untested exports and globals it already had at the parent do not fail the change that made it load again. A parent that did not compile is the usual case: the next commit fixes it and every package the break skipped would otherwise read as new. The report prints one line per such package, `baseline unavailable for <package>: <reason>; ratchets skipped`, where the reason is the kind of load failure and its first error, in the text and hook output, as a `::notice` in the GitHub format, and as `baseline_unavailable` on the package's report in the JSON (10.2); its summary line ends `baseline unavailable` where a new package's says `new since baseline`. A baseline that does not load at all is no baseline: the check fails, or a replay judges the commit against an empty baseline (11.3), as before. A baseline file records no load failures, so every package it lacks is new.

The rebuild estimate is not gated directly. It mixes size and density terms, so a large well-written feature raises it; it stays a ranking and summary signal. The capacity ceilings below bound two of its five terms and do not ensure one pass: `tokens_est` caps the volume term and `exported_symbols` the contract term, so at the default ceilings (8.2) those two come to at most 16,000 + 60 × 40 = 18,400 tokens, leaving 19,100 of the 37,500-token context budget for the spec, unspecified and hidden terms, which no ceiling bounds. Nor is a ceiling breach a failed pass: duplication shrinks the volume term, so this repository's `internal/metrics`, at `tokens_est` 16,694 with 42.4% of it duplicated, scored 0.9 agent passes (ONE_PASS) on 2026-09-28 while over the `tokens_est` ceiling.

Any violation fails the gate with exit code 3. Warnings, a `warn` rule's included, never change the exit code. Violations and warnings are reported one per line with metric, baseline value, head value, limit and a fix suggestion.

### 8.3 Baselines

Two sources, chosen by flag:

- `--base <ref>` (default): the merge-base of `HEAD` and `<ref>` (default `origin/master`, then `master`, `origin/main`, `main`). The base tree is checked out into a temporary `git worktree`, analyzed, and removed. Packages are matched by their directory relative to the module root, the `package_path` of 10.2, not by import path: for Go the base tree's own `go.mod` gives the module path its import paths are made relative to, so a module-path change between base and head (a `/vN` bump) leaves every package matched. The `<module>` row keeps its id (8.1). A package that moved to another directory has no row of its own; 8.4 says when it is seeded from the packages it was renamed from.
- `--staged` changes the head, not the baseline: the head tree is the git index rather than the working tree. `git checkout-index -a` copies it (the index `GIT_INDEX_FILE` names, when a hook sets it) into a temporary directory, which is analyzed and removed. `--staged` requires a git repository.
- `--baseline <file>`: a committed `.astimate/baseline.json` written by `astimate baseline write`. For repositories that prefer explicit, reviewable baselines or that run outside git. The file records the tokenizer used to write it; `check` warns when its own tokenizer differs, since token counts from different tokenizers are not comparable. A baseline file also records each package's functions (receiver, name, a 16-hex-digit fingerprint, cognitive complexity and cyclomatic complexity, the last absent from files written before it existed) under a top-level `functions` key, so a check against it can compute `changed_func_cognitive_max`; a file without the key still loads, leaves that metric null and says so once on stderr. Git baselines carry the same records in memory. The `packages` and `functions` keys are import paths (the extractor's package identifiers); a top-level `package_rows` object, keyed the same way, holds each package's own record, `{"package_path": "<dir>", "dup_blocks": ["<16 hex digits>", ...], "untested_exports": [<names>]}`, and a check matches by that `package_path`; `dup_blocks` holds the anchors of the package's duplicate blocks and `untested_exports` names its untested exports (8.4), both absent from a file written before they existed, against which a check cannot tell what a change added and keeps the order of assess. Git baselines carry the same records in memory. A file without `package_rows`, written before it existed, still loads: each directory is taken from the file's `module_path`, and one warning on stderr says so (`baseline file keys packages by import path only; run \`astimate baseline write\` to record each package_path`).

### 8.4 Changed-package detection

`git diff --name-only <merge-base>` (the working tree against the merge-base, so committed, staged and unstaged changes all count) plus untracked non-ignored files, mapped to packages by directory. Rename detection is disabled so a moved file shows both its old and new directories. Files map to packages by the extractor's file rules (`metrics.SourceClassifier`): for Go, a `.go` file selects its directory and paths under `testdata` are ignored; for TypeScript, a source, test or declaration file selects the package that 13.1 assigns it to, the root `package.json` or any `tsconfig*.json` selects every package, and `node_modules`, `dist`, `build` and dot directories are ignored. Paths inside a nested module (a directory below the root holding the extractor's module marker, `go.mod` or `package.json`) are ignored, and the set is intersected with the packages the extractor lists, which for Go drops `_`-prefixed, `.`-prefixed and `vendor` directories. A directory left with no file that makes it a package is reported as deleted in a summary line, never as a violation. An extractor without file rules gets every package checked, with a warning. A changed TypeScript declaration file (`.d.ts`, `.d.mts`, `.d.cts`) can change where other packages' imports resolve, so it also selects the packages that import its package from non-test files in the head import graph (the edges `fan_in` counts, through the optional `ImporterLister`), and a log line names the package each was selected for; the changed-file listing is `git diff --name-status`, so a deleted declaration file is told apart from an added one, and a git baseline records the merge-base reverse import graph when it is extracted; the importers of a removed declaration file's package are taken from that graph, and those of a changed one's from the union of the head and merge-base graphs, so the importer whose import turned external (its `external_imports` rose) is selected, with a log line saying it is an importer at baseline. A baseline file records no import graph, so against one a removed declaration file's former importers are not selected and one info line says so. Go selects no importers: an import path names its package whatever files it holds, so an importer's `internal_imports` changes only through its own import declarations, whose change selects it, and a removed exported symbol breaks the importer's build rather than moving its gated metrics. A change to a package's test files alone still selects it. `--all` overrides. With `--baseline <file>`, the merge-base is taken against the ref the file records; if it records none or the ref does not resolve, every package is checked and a warning says so. With `--staged`, changed files are `git diff --name-status --cached <merge-base>`: staged changes only, with untracked files excluded, mapped by the same file rules. A directory counts as deleted when the index copy has no file that makes it a package. `--all --staged` checks every package of the index copy. **Skipped packages** (6.5) follow the same rule under every selection: one is selected only when its own files changed (a test file counts), so `--all`, an extractor that cannot tell what changed, a baseline file with no usable ref and a change that can move every package select the packages that load and leave a skipped one out, reported with `selected` absent (false), and a change to the skipped package itself selects it under any of them. **No hooks.** Every git command astimate starts, the baseline worktree (`git worktree add --detach`) and the staged copy (`git checkout-index`) included, runs with `-c core.hooksPath=/dev/null`, so none of the repository's hooks runs (a `post-checkout` hook that needs `git-lfs` would otherwise fail a checkout that is read-only scaffolding); the setting is an argument, never an environment variable or a change to the repository's config.

**Renamed packages.** Selection lists a moved file on both sides, but the baseline is keyed by directory (8.3), so a package carved out of another by moving files would be judged as new: every `max` applies, `ratchet_from_zero` rules count from zero and `has_tests` fires. When a checked package has no baseline row of its own, its row is seeded from git instead. `git diff --name-status -M -C <merge-base>` (with `--cached` under `--staged`; against the working tree, only renames git tracks count, so an untracked moved file is not one) lists the renames between the merge-base and head, a rename edited after the move counting while git still pairs it (50% similarity), and a copy counting as a rename: git lists a copy only from a file the same diff modified, which is how code moved out of a file that keeps its path into a new file reads (a leaf package carved out of `observe.go`, `observe.go` still in place), while a copy of a file the change did not touch is not followed; a rename counts when both its old and new path are non-test files that make their directory a package (for Go any `.go` file not ending in `_test.go`, `metrics.SourceFile.Test`), in different packages, and inside the module: a rename from or into another module, a nested one included, is not followed, and a package whose files are all new stays new. A head package that such renames came into, from one or more baseline packages that have a row, is judged against a seeded row: the metrics of the source package most renamed files came from (ties go to the lexically first directory), the functions of every source, for `changed_func_cognitive_max`, the duplicate blocks and untested exports of every source when every source recorded them and none otherwise (a source without them would read all of its blocks as added), so a function moved with its file is matched to its own baseline function and judged against that function's complexity (8.1). The seeded row serves every package rule, density, capacity and requirement alike, so a moved file that had tests and duplicates before does not fail `has_tests` or `dup_blocks`, and a carved-out package is held by the ratchet and the legacy rules of the package it came from; the `<module>` row and its rules are unchanged. The report records the sources as `baseline_from` (10.2), and the text summary line ends `baseline seeded from <dirs> (rename)`. An import edge from a source package to a package carved out of it in the same change is not a rise: the source's baseline `internal_imports` counts each carved-out package it imports at head, and the seeded row's `fan_in` counts each source importing it, both from the head import graph (`ImporterLister`; without it neither is adjusted). Nor is the edge of a package that imported a source at the baseline and imports both that source and the carved-out package at head: it imported the code before, and the split only renamed where it lives, so its baseline `internal_imports` counts the carved-out package too. The baseline's import graph (8.3) says who imported the source; a baseline file records none, so against one only the source's own edge is exempt. A package that imports the carved-out package without having imported a source still counts the edge, and one that swapped its import of the source for the carved-out package has no rise to exempt. With a baseline file, renames are taken against the merge-base of the file's ref, and none are followed when it records no ref or the ref does not resolve.

**What the change added.** A check cites first what the change added, so an agent following a suggestion edits its own code rather than legacy code. The baseline records each package's duplicate blocks and untested exports (8.3; a seeded row takes those of every source). A block's identity across commits is its two anchors: hashes (FNV-1a, 64-bit) of the first and of the last `duplication.min_tokens` tokens of its normalized token sequence (6.3), keyed per token by a value that is the same in every load (the Go token kind; for TypeScript the token kind's name hashed, since its stream codes are interned per load). duptok had no fingerprint over normalized tokens to reuse; the per-function fingerprints of `changed_func_cognitive_max` hash function bodies, not blocks. A head block is added in this change when neither of its anchors is among the anchors of the package's blocks at the baseline: this is the reading taken of "none of its occurrences lies inside a baseline block", since lines move between commits and cannot be compared. Hashing the ends rather than the whole sequence keeps a legacy block legacy when a change moves one of its ends: a maximal repeat grows by a token when an edit makes the tokens after its copies agree, as appending a function after the last copy does, and shrinks when an edit cuts into one copy, and either way the other end is unchanged. A block both of whose ends changed, or any block when `duplication.min_tokens` changed between the commits, reads as added. In `dup_blocks` and `duplication_pct` findings the added blocks rank before every legacy block, each part in the size order of 10.2; an untested export is added when the baseline did not list it as untested, and `untested_exports` names the added ones first, each part sorted. A package the baseline lacks added all of them. A cross-package block (`dup_blocks_cross_pkg`) is new when more head blocks than baseline blocks touch its set of packages, and the module rule judges as added only the new ones at least `duplication.min_tokens_cross` long that no rename moved (8.1); the new ones rank first, each part in order of first occurrence. A baseline file records no cross-package blocks, so against one their order is unchanged. `assess` has no baseline and keeps the size order.

### 8.5 Output formats

- `text` (default): violations, then warnings, then a one-line summary per package: `<pkg>: N violations, M warnings, K exempted`, with `, new since baseline` for a package the baseline lacks. When the rebuild estimate is calibrated (`rebuild.calibrated`, 10.2), the line leads the counts with `<agent_passes> passes (<tier>)` and ends with `, ±X passes from baseline`; while it is uncalibrated, gate output leaves the estimate out, since its invariants (7.5) can contradict the gate. The `hook` reason and `github` annotations carry findings only, never passes or tier. An `exempted:` section follows the warnings, each line ending `Exempted: <reason>` (8.6).
- `json`: the section 10.2 report per package plus `violations`, `warnings` and `exemptions` arrays and a `passed` bool.
- `hook`: the JSON shape Claude Code Stop hooks consume: `{ "decision": "block", "reason": "<violations as text>" }` on failure, `{}` on success, so the agent is told to keep working and why. Warnings are appended to the reason on failure and written to stderr; exempted violations, each with its reason, are in the reason on failure and written to stderr on success on success. Because Claude Code reads a hook's JSON only when it exits 0, `--format hook` exits 0 whenever it produced a decision, whether or not there were violations; analysis failure still exits 2, which a Stop hook treats as a blocking error with stderr shown to the agent. In hook format, `check` reads the Stop hook's JSON from stdin when present and emits `{}` without analysis when `stop_hook_active` is true, so a hook that already blocked once never blocks again.
- Skipped packages (6.5): every format lists each package that does not load after the findings, as `<pkg> skipped, it does not load (<reason>): <first error>`, ending `; it is among the packages this check judges, so the verdict is incomplete` when the check selected it (its own files changed since the baseline; `--all`, or a change 8.4 lets move every package, does not select a skipped package that did not change, which is listed unselected): one line in `text`, one `warning: ` line in the hook's reason or stderr, one `::warning file=<pkgdir>` annotation in `github`, and in `json` a `skipped` array on the module row (10.2). `text` says `no changed packages` only when no skipped package was selected either.
- `github`: `::error` annotations, one per violation, `::warning` per warning, and `::notice` per exempted violation, located like a violation with its message ending in the reason, each on the file and line that caused it where the extractor can say: a duplicate block's occurrence for `dup_blocks` and `duplication_pct`, the untested export's declaration for `untested_exports`, the global's declaration for `globals`, the largest file for `sloc`, `largest_file_sloc`, `tokens_est` and `tokens_est_with_tests`, the function for `changed_func_cognitive_max`, else the package's `doc.go` or first file; among several candidates, the first in a file holding a changed function, except that a `dup_blocks` or `duplication_pct` finding whose first block the change added is located on that block's first occurrence, and an `untested_exports` finding whose first export the change added on that export, wherever the changed functions lie (8.4). A finding with no location is annotated `file=<pkgdir>`. Paths are relative to the repository top level (the module root's directory in the git repository is prefixed; outside git, paths are module-relative). The module row's findings lead with `module: ` (the row's id, `<module>`, is used in every other format); a `dup_blocks_cross_pkg` finding is annotated on the first occurrence of the first cross-package block in the order of 8.4, the first one the change added when the baseline recorded its blocks, when the extractor names them, and otherwise carries no `file` property. When the baseline's tokenizer differs from the check's, one `::warning title=astimate::` line says token counts are not comparable; the hook format adds the same text as a `warning:` line.
- A `warn` rule's breach (8.1) is a warning in every format, with the line and location its violation would have had: under `warnings:` in `text`, in `check_package`'s text and in the hook's reason or stderr, a `::warning` annotation in `github`, and an entry of `warnings` carrying `"severity": "warn"` in `json`.
- `md`: the Markdown of the module report's change block (10.3) for a pull request comment or a step summary, built from the check as `engine.WriteChange` does (the whole module is extracted once more, as `report --base` does, for the packages' ranks): a heading with the verdict and counts, a table of the findings (package, what moved, base → head, where to open), one line of heads-ups by rule with the passed count and the module's cross-package copies at base and at head. Exit codes are `check`'s.
- `github` annotation cap and summary: at most ten `::error` annotations and ten `::warning` annotations are written (GitHub shows ten of each per step and drops the rest), taken in the order the module report ranks its failing packages (most findings first, then hotspot; the module row ranks with them), the findings of one package in their own order; the rest are not annotated, and a last plain line says `astimate: N more findings and M more warnings are not annotated; the report lists them all`. When the `GITHUB_STEP_SUMMARY` environment variable names a file, the `md` text, followed by that line as a sentence when something was left out, is appended to it. Without the variable, and within the cap, the output is unchanged.

### 8.6 Exemptions

An optional top-level `exemptions:` list accepts one rule's violations on one row, with the reason recorded beside it. Each entry has `package` (a package directory relative to the module root in slash form, as `package_path` shows it: `internal/x`, `.` for the root package, or `<module>` for the module row), `metric` (a metric some threshold gates, at the top level or in a `languages:` override; a module-wide metric only with `<module>`, every other metric only with a package), `reason` (required, not blank) and optional `expires` (a `YYYY-MM-DD` date; the exemption applies through that day). Each entry is validated on its own and its errors name its index (`exemptions[2]: reason is required`). A `languages:` override carries no exemptions; the list applies to every language.

After a row is evaluated, each violation whose row and metric match an unexpired exemption moves from `violations` to the row's `exemptions`, carrying the first matching exemption's reason; `passed` is computed from the violations left, so a row whose violations are all exempted passes. A `warn` rule's breach (8.1) is matched the same way and moves from `warnings` to `exemptions`, keeping its `severity`, so the exemption is used, not stale. Other warnings are never exempted: they never fail, so an exemption on a capacity rule matches only its violation. A finding that merged other rules' findings (8.1, its `also`) moves only when every rule it carries, its own and each in `also`, is matched by an unexpired exemption, since each would have failed on its own; it carries the reason of the first matching exemption in list order, and an exemption matching only some of its rules is still counted as used, so it is not reported stale. An exempted violation stays visible, with its reason, in every format (8.5). An expired exemption is ignored, so its violation fails again, and every check reports it as a warning on its row (`limit` `exemption expired <date>`) when the check has that row, otherwise as a warning on stderr. A check with `--all` judges every row, so it also reports each unexpired exemption that matched no violation as a warning (`limit` `stale exemption`) on its package or, for a package the module does not have, on the `<module>` row (on stderr when there is no module row); the notice names the exemption and its reason. An exemption is not called stale when its row could not be judged: the package failed to extract, the checked language gates no rule on its metric, the metric is null on the row, or the module row's rules were skipped. A check of changed or named packages, including `check_package`, reports nothing stale, since the rows it did not select were never evaluated. Exemptions are a person's decision, visible in review; `docs/reading-violations.md` tells agents never to add one to pass the gate.

## 9. CLI

```
astimate check    [<module-root>] [--base ref | --baseline file] [--all] [--staged] [--config|--thresholds file] [--format text|json|hook|github|md] [--tokenizer=est|o200k] [--coverage] [--coverage-timeout 2m]
astimate baseline write [<module-root>] [--out .astimate/baseline.json] [--tokenizer=est|o200k]
astimate assess   <package-dir> [--json] [--config astimate.yaml] [--tokenizer=est|o200k] [--coverage] [--coverage-timeout 2m]
astimate rank     [<module-root>] [--json] [--top N] [--sort passes|days|fan_in|tokens|duplication|churn] [--config astimate.yaml] [--tokenizer=est|o200k] [--coverage] [--coverage-timeout 2m]
astimate report   [<module-root>] [--base ref] [--format json|md] [--config astimate.yaml] [--tokenizer=est|o200k]
astimate dryrun   [<module-root>] [--last 50] [--budget 10] [--suggest file] [--json] [--timeout 30m] [--parallel 1] [--config astimate.yaml] [--out dir]
astimate serve    [--config astimate.yaml] [--allow-any-path]
astimate config init [--out astimate.yaml]     # rebuild parameters and thresholds in one file with comments
astimate version
```

Exit codes: 0 success or gate passed, 1 usage error, 2 analysis failure, 3 gate failed (except `--format hook`, which exits 0 with a decision; see 8.5). When a violation and an analysis failure both occur, 3 wins because a verdict was reached. A package that does not load (6.5) is an analysis failure of `check` only when the check selected it, since its verdict would then be incomplete; otherwise it is listed and the packages that load decide the exit code. Logs go to stderr only. `rank` defaults `<module-root>` to the current directory and ranks the whole module containing it; `--top 0` (the default) prints every row; a package whose extraction fails is logged and omitted, and the command exits 2 after printing the rest. `dryrun` replays the last `--last` first-parent commits of `HEAD` of the repository holding `<module-root>` with the replay of 11.3 (package `internal/replay`), each checked against its first parent in a temporary worktree under the resolved configuration, and prints the share of the commits it checked that the gate would have failed, which is the share `calibration/validate` (11.4) reports for the same rows, and the same failures as a share of the checked commits that changed or deleted a package; per rule (a rule is its metric, top level and `languages:` overrides alike) the commits it failed, its own violations or merged into another finding's `also` (8.1), its share of the commits checked and the commits it alone failed; the five packages, module row included, with a violation in the most commits; and the commits it could not check (the module or the baseline did not load, or the check selected a package that does not load, 6.5) with their errors. `--suggest <file>` writes the resolved configuration file (the embedded default when none) with `severity: warn` on every rule on a metric whose share exceeds `--budget` percent, and on every other rule whose every violation was merged into by a rule over budget (its `also` list, 8.1, holds an over-budget metric: the merged finding is attributed to the other rule, which would keep failing the commit if only the over-budget rule warned), comments kept, after checking that it parses; `--json` prints instead the replay's rows as JSON lines, each commit's `packages.jsonl` rows followed by its `commits.jsonl` row (a package row is a line with a top-level `package` key), which the calibration tools read once split into the two files; `--out <dir>`, which must be new or empty, keeps the replay's `commits.jsonl`, `packages.jsonl` and `run.json` there in the format of 11.3, which `calibration/replay/label` and `calibration/validate` read as they read a calibration replay. The replay builds into a Go build cache and temporary directory of its own (`GOCACHE` and `GOTMPDIR` in the process environment, package `internal/gocache`), removed when `dryrun` ends, so the user's cache does not grow. `--timeout` (0 for none) bounds the whole replay and `--parallel` the commits replayed at a time. `dryrun` exits 0 whatever the gate would have said, 1 on a usage error, and 2 only when the replay itself fails, or stops at `--timeout` or on an interrupt, in which case it still prints what it replayed.

Config resolution: `--config <path>`, then `./astimate.yaml`, then the embedded default. Top-level keys (`config_version`, `chars_per_token`, `rebuild`, `thresholds`) are required; missing ones are errors rather than being filled from the default, and `config init` writes a complete file to start from. Sections that group optional tuning (`duplication`, with `min_tokens`, `min_tokens_cross`, `ignore_literal_only`, `fold_signs`, `split_literal_runs`; a negative `min_tokens_cross` is an error, 0 turns the floor off; `churn`, with `commits`, the window of 6.6, default 200, 0 turning churn off and a negative value an error) may be partial or absent; absent keys take the embedded defaults. A capacity rule takes `max`, `warn_at` (default 0.75) and `over_max_delta` (default 0; 8.1); `over_max_delta` on a density or requirement rule is an error naming the rule, as is a negative or non-finite value. Every rule takes an optional `severity`, `fail` (the default) or `warn` (8.1); any other value is an error naming the rule, and a `languages:` override's rule sets its own, the replaced rule's not carrying over. The pre-1.0 top-level `dup_*` keys are accepted with a deprecation warning for one release and rejected when the section is also present. An optional `languages:` section, keyed by language id (the ids the registered extractors report, today `go` and `typescript`), overrides the configuration for one language. Its `rebuild:` sets only the parameters it names, the rest coming from the top-level `rebuild`. Its `thresholds:` rules replace the top-level rules on the same metric, in the first one's place, or add a rule; a rule of the form `- metric: <name>` with `disabled: true` drops the top-level rules on that metric for the language, and `disabled` is an error at the top level. `chars_per_token`, `duplication` and every other setting are shared. Each override is validated on its own, after merging, and its errors name the language; the config parser accepts any id, and the engine warns once for an id no registered extractor reports. A report judged with an override shows `config_version` suffixed with `+<language>` (for example `thresholds-2026-09-28+typescript`). `config init` writes the embedded default's `typescript` override (section 8.2) and a commented example of the other keys. An optional top-level `exemptions:` list (8.6), each entry `package`, `metric`, `reason` and optional `expires`, accepts named violations with a recorded reason; the embedded default has none, `config init` writes a commented example, and a `languages:` override cannot carry one.

### 10.2 Report schema

```json
{
  "language": "go",
  "package_path": "internal/billing",
  "module_path": "github.com/acme/app",
  "role": "library",
  "rebuild": {
    "agent_passes": 2.4,
    "rebuild_tokens": 61000,
    "human_days": 9.5,
    "tier": "FEW_PASSES",
    "calibrated": false,
    "drivers": [ { "term": "unspecified", "tokens": 5600, "detail": "untested_exports=7" } ]
  },
  "suggestions": [ "7 exported functions have no test; a rebuild would have to reverse-engineer their behavior." ],
  "metrics": { "...": "every field from section 6" },
  "baseline": { "ref": "a1b2c3d", "tokenizer": "est", "tokens_comparable": true, "metrics": { "...": "same fields" } },
  "violations": [
    { "metric": "dup_blocks", "base": 1, "head": 4, "limit": "max_delta +0", "suggestion": "..." }
  ],
  "warnings": [
    { "metric": "tokens_est", "head": 24100, "limit": "max 30000", "suggestion": "at 80% of the ceiling; plan a split before the next feature" }
  ],
  "exemptions": [
    { "metric": "globals", "base": 0, "head": 1, "limit": "max_delta +0", "suggestion": "...", "reason": "the registry is process-wide by design" }
  ],
  "passed": false,
  "astimate_version": "0.3.0",
  "config_version": "thresholds-2026-10-14b"
}
```

`check --format json` lists the module row first as an ordinary report whose `package_path` is `<module>` (written without HTML escaping): v0 metrics are 0 and v1 metrics are null except the module-wide ones, and its rebuild block is zero. The module row alone may carry `"skipped": [{package, reason, error, selected?}]`, the packages that do not load (6.5), `package` in the form of `package_path` and `selected` true when the check would have judged it; it is omitted when none was skipped, so the change is additive. A check with no module row, one that selected nothing, reports them on stderr only. `metrics.changed_func_cognitive_max` is filled only by `check` (null in `assess`), `baseline.metrics` never carries it. `metrics.churn_commits` and `metrics.churn_authors` (6.6) are filled at HEAD by every operation, and `baseline.metrics` carries them only from a baseline file that recorded them, never from a git ref. Its finding's `base` and `head` are those of the changed function the rule judged (8.1), so it has a `base` only for a function that existed at the baseline, and the text format renders one without a `base` `head (changed since baseline)`; the finding is located on that function and its suggestion names it.
`config_version` carries a `+<language>` suffix when a `languages:` override applied (section 9). A `dup_blocks` or `duplication_pct` suggestion cites the first occurrence of the first duplicate block in the order of `details.duplicates` (`..., starting with <file>:<start>-<end>`) and, in `check`, follows the citation with `, added in this change` when the change added that block (8.4); a `dup_blocks_cross_pkg` suggestion does the same for the pair of occurrences it cites. `baseline.tokenizer` is the tokenizer the baseline counted tokens with, and `baseline.tokens_comparable` is false when it differs from the check's, in which case token deltas against the baseline are not meaningful; the gate still runs.

A finding of a rule with `source: coverage` that judged `untested_exports_covered` (8.1) has metric `untested_exports`, the covered counts as `base` and `head`, and a `limit` ending in ` on untested_exports_covered`, such as `max_delta +0 on untested_exports_covered`. Each finding in `violations` and `warnings` may carry `"location": {"file": string, "line": int}`, `file` relative to the module root and `line` 0 when only the file is known; it is omitted when the finding has no location. A report may carry an optional top-level `"details"` object, omitted when the extractor records none or the row has nothing to show, with every inner key also omitted when empty (`functions`, `[{name, file, line, cognitive, cyclomatic}]`, lists the package's functions in declaration order with the per-function values behind `cognitive_total`, `cognitive_p90`, `cyclomatic_total` and `cyclomatic_p90`, `name` prefixed with the receiver and a dot for a method, `file` relative to the package directory): `duplicates` (`[{file, start_line, end_line}]`, one entry per occurrence of each duplicate block, ordered by the block's length in tokens, longest first, ties in file order, so the first entry is the copy worth extracting and the one a suggestion cites; in `check`, the blocks the change added come first, 8.4), `untested_exports` (`[{name, file?, line?}]`, sorted by name; in `check`, those the change added first), `excluded_untested` (`[string]`), `globals` (`[{name?, file?, line?}]`, `name` being the variable's name when the extractor records it), `largest_file` (string) and `cross_blocks` (`[{occurrences: [{package, file, start_line, end_line}]}]`). Files inside `details` are relative to the package directory, as the extractor's `Details` gives them, except `cross_blocks` occurrence files, which are relative to the module root; `package` is the module-relative directory in the same form as `package_path`. On the module row, `details.cross_blocks` lists every cross-package block in the module, in order of first occurrence, or in `check` against a baseline that recorded its blocks with those the change added first (8.4). Text and table outputs do not render details.

`package_path` is the package directory relative to the module root (`.` for the root package); the full import path is `module_path` joined with it. Baselines match packages by `package_path` (8.3). A `check` report may carry `"baseline_from": [<dirs>]`, the sorted `package_path`s of the baseline packages its `baseline` block was seeded from because its files were renamed from them (8.4); it is omitted otherwise, so the change is additive. A `check` report of a package that existed at the baseline but failed to load there carries `"baseline_unavailable": "<reason>"` and no `baseline` block (8.1); it is omitted otherwise, so the change is additive. `agent_passes` and `human_days` are rounded to one decimal; `rebuild_tokens` and driver `tokens` are integers. `rebuild.calibrated` is true when `config_version` starts with `rebuild-`, the prefix section 11.2 assigns to measured rebuild parameters, or is a gate retune `thresholds-<date>` dated after the rebuild fit of 2026-09-28, which kept the fitted parameters it was made on (the shipped `thresholds-2026-10-14b`, and any `+<language>` suffix); a `thresholds-<date>` version dated on or before it carries the placeholder parameters and reports `false`, because the flag describes the estimate's parameters, not the gate. `passed`, `baseline`, `violations`, `warnings` and `exemptions` are present whenever a gate ran, with `violations`, `warnings` and `exemptions` as empty arrays rather than omitted; all five are absent from `assess` output. `exemptions` lists the violations an exemption silenced (8.6): each a finding with a violation's fields, `location` included, plus `reason`. A capacity finding on growth of a package already over its `max` under a non-zero `over_max_delta` (8.1), warning or violation, has `limit` `over max by N, allowed M`; the schema is unchanged. `warnings` may also carry the notices of an expired or stale exemption, with the same fields and `limit` `exemption expired <date>` or `stale exemption`. A finding may carry `"severity": "warn"`: it is present only on the breach of a `warn` rule (8.1), in `warnings`, or in `exemptions` when an exemption matched it, and omitted from every other finding, violations included. A finding may carry `"also": [string]`, the metrics of the rules whose findings of the same cause the gate merged into it (8.1), such as `["tokens_est"]` on a `sloc` finding or `["duplication_pct"]` on a `dup_blocks` finding; it is omitted when nothing was merged, and its `limit` names each merged rule's values and limit. `explain_metric` returns `merged_into`, the metric a finding of the explained one is attributed to when both fire, omitted for a metric merged into no other; `rises_when`, what must hold for a density rule on it to fail a rise against a baseline (8.1), omitted when any rise is judged; and each threshold's `floor` when it has one and its `roles` when it has them, its text saying which roles the rule judges. A report carries `role`, the package's role (6.5), beside `package_path`; it is omitted on the module row and when the extractor records none, and it is not in `metrics`, which holds the section 6 fields only. A replay row carries the same `role`. The changes are additive: `violations`, `warnings` and `passed` keep their meaning, and `passed` counts only violations.

### 10.3 Reports

`astimate report` describes a whole module in plain words, and with `--base <ref>` the change against the merge-base of `HEAD` and that ref, for a first look, a periodic review, CI, a hook or a pull request. Package `internal/narrate` holds the module report's types and `internal/narrate/compose` builds it from the engine's results (`engine.Report`): every package extracted once with its report and `details` as `assess` builds them (10.2) and its churn from one history walk (6.6), and with a base the check of the changed packages exactly as `check --base <ref>` selects and judges them (8.1, 8.4). Every renderer (`--format json` and `md` today; text and HTML later) renders this one report, so every format says the same words. `narrate` imports `internal/report` only and `compose` imports `narrate`, `report` (and its `rows` and `details`) and `metrics` only, never an extractor, `score`, `gate` or `baseline`; import-boundary tests enforce both. `report` exits 0 when it printed the report, whatever the change's verdict (it reports, `check` gates), 2 on an analysis failure or when a package failed to extract, which is logged and left out while the rest is printed, and 1 on a usage error; without `--format` it writes a one-line notice to stderr that text output is coming and prints the JSON.

`head` is the commit at `HEAD`, omitted outside git or before the first commit; `change` is omitted without `--base`; a text that would be empty is omitted (a package's `changes`, `copies.longest`, `complexity.say`, a driver's `label`, a finding's `moved` and `moved_short`, the change's `base_commit`), as are a finding's `location` and the change's `deleted` when there is none; every other key is always present, `churn`, `copies.code_blocks`, `complexity.buckets`, a finding's `base`, `over_by` and `allowed` and the change's `cross` as null when unknown. `packages` is sorted by `path`. `name` is the last element of `module_path` that is not a major-version suffix (`v2` and above), or the module root's directory name when there is no module path, with its first letter upper-cased. The report's rules, each number shipped as stated:

- **Ceilings.** The five size metrics `sloc`, `tokens_est`, `largest_file_sloc`, `exported_symbols` and `internal_imports`, each against the `max` of the first rule on it that has one in the configuration of the module's language (config, section 9). A ceiling is `judged` when its rule judges the package's role (6.5; an empty role is a library), and `over` when judged and the value exceeds `max`. A ceiling's `level` is `split` when over, `watch` at 80% of `max` or more, else `fine`.
- **Band.** `split` when the rebuild tier is `PARTITION` or the package is over two or more ceilings; `watch` when it is over one, or the tier is `FEW_PASSES`, or `duplication_pct` is 25 or more; `fine` otherwise. `counts` sums the bands and the packages without tests, and `human_days` is the sum of every package's `human_days`, rounded to a whole day.
- **Hotspot.** `churn_commits` times `human_days`, to one decimal; 0 when churn was not measured. `hotspots` lists the five highest, ties by `human_days` (higher first) then path; "start here" is its first three.
- **Human time.** One engineer's working days, at 5 a week, 21 a month and 220 a year: under 5 days as days (at least 1), under 21 as weeks, under 220 as months, else engineer-years, each rounded to a whole number and singular for 1 (`human_time`); `human_short` is the same as `d`, `wk`, `mo` or `yr`, the years to one decimal.
- **Sittings.** An agent rebuild of at most 1 pass is `one sitting`, of at most 3 `a few sittings`, of more `split it first`; `sittings_text` is `one sitting` up to 1 pass, else the passes rounded up and `sittings`.
- **Drivers.** Each rebuild driver's `tokens` as a whole percentage of `rebuild_tokens`; `spec` is labelled "the tests it must satisfy" and `volume` "the amount of code", the others unlabelled.
- **Copies.** `level` is `split` at a `duplication_pct` of 25 or more, `watch` at 10 or more, else `fine`. `chunks` are the two longest occurrences in `details.duplicates` by line count (ties in its order), an occurrence dropped when one already chosen is in the same file with a `start_line` in the same run of ten lines (`start_line / 10`).
- **Complexity.** Each function of `details.functions` is easy at a cognitive complexity up to 10, needs care from 11 to 20 and is hard over 20 (`buckets`, null when the extractor recorded no functions); `hardest` are the three with the highest cognitive complexity, ties in declaration order, each with the `level` of its bucket (`fine`, `watch`, `split`).
- **Change.** `changed` counts the packages the check selected and `unchanged` the rest; `failing` lists each row with violations, the module row as `<module>`, most violations first then by hotspot; `warning_groups` groups the warnings by metric, the largest group first then by metric; `passed_paths` are the changed packages with no finding; `verdict` is `FAIL` when any row fails, else `PASS`; `cross` is the module row's `dup_blocks_cross_pkg` at base and head. A finding's `over_by` and `allowed` are read from the first clause of the gate's `limit`, `over max by N, allowed M`, and are null for any other limit.

The sentences are kept in one Go file (`internal/narrate/compose/sentences.go`) and are the report mockup's (`docs/design/report-mockup-2026-10-14.html`). A sentence never states a number its row does not carry: a clause whose number is missing is dropped (the hottest-package sentence of `lead`, a package's `changes` and its `Changes` fact without churn, the glossary's `Limits`, `Copied` and `Changes` entries without their settings), and counts are singular for 1. Numbers are written en-US, thousands separated, with at most one decimal.

- `story`: "It is over N of its five limits (labels)", "It is over its <label> limit" or "It is inside every limit", joined by ", and " with "<duplication_pct>% of its lines are copies of each other" at 20% or more, "<untested> of its <exports> exports have no test" at 5 or more, and "it has no tests at all" when it has none. The labels are size, tokens, largest file, exports and imports.
- `todo`: Split, "Extract the copied code first, then split the package along its responsibilities." at 20% copied, else "Split it into smaller packages before the next feature lands here."; Watch, "Plan a split now; the gate fails the next change that grows it." when over a ceiling, else "Nothing yet. Keep an eye on it."; Fine, "Nothing. Leave it alone."
- `changes`: "It changed N times in the last W commits, so every one of those problems is in the way of day-to-day work."
- `rebuild.say`, by sittings band: "Small enough that an AI agent could rewrite it from its tests in one sitting.", "An agent would need about <sittings_text>, carrying notes between them." or "Too big to rebuild as it stands: an agent would need about <sittings_text>, so the package has to be split first.", each followed by "For one engineer, about <human_time>."
- `copies.say`: at 40% or more "Nearly half of this code exists at least twice. A bug fixed in one copy stays alive in the others, and every copy is more for a rebuild to read.", at 20% "A large share of this code exists at least twice. A bug fixed in one copy stays alive in the others.", at 5% "Some of this code is repeated. Worth extracting when you are next in here, not urgent.", else "Very little repetition. Nothing to do."; `copies.longest`: "Longest repeat: <file>:<start>-<end> (<lines> lines), again at <file>:<start>-<end>."
- `complexity.say`, empty for a package with no functions: "Every function here is easy to follow.", "Most functions are easy to follow; N need some care." or "N functions are hard to follow: they branch and nest enough that a rewrite would likely get them wrong. Start with the ones below." (none of these without `buckets`), then "The hardest tenth of functions score <cognitive_p90> or more; code nests up to <max_nesting> levels deep."
- `facts`: Rebuild, Copies, Complexity, Tests, Changes (with churn) and Used by, each one line of the package's numbers.
- `headline`: "<Name> has N packages too big to rebuild in one go. Start with <first hotspot>." or "<Name> has no package too big to rebuild in one go."; `lead`: "N packages, about <human_time> of one engineer's time to rebuild from their tests. F are fine, W are close to a limit, and S need a split.", then, for the split package with the highest non-zero hotspot, "The hottest of those changed C times in the last W commits and P% of it is copied code."
- Change `headline`: "N packages need attention before this merges." or "Nothing needs attention before this merges."; `lead`: "N packages changed. F fail the gate with V findings. P pass clean", ending ", and nothing new was left untested." when no finding is on `untested_exports`; `passed_summary`: "P changed packages pass clean, U did not change"; a failing row's `summary`: "N findings · <human_days> days to rebuild · C changes lately", the last two when known.
- A finding's `why`, for `dup_blocks`, `sloc`, `largest_file_sloc`, `exported_symbols` and `changed_func_cognitive_max`, says why the gate cares (empty for other rules); `do` is the first clause of the gate's suggestion; `moved` is "grew G, allowed A while over the limit" for an over-max limit, or for a `dup_blocks` finding under `max_delta +0` "N new duplicate blocks; the rule allows none" (`moved_short`: "grew G, allowed A", "N new copies, none allowed"), empty without a base. A warning group's `why` says what the warning means for `sloc`, `tokens_est`, `largest_file_sloc`, `exported_symbols`, `internal_imports`, `untested_exports`, `globals` and `cognitive_p90`, quoting the ceiling.
- `glossary` (served by `compose.Glossary` for later use by `explain_metric`): Rebuild cost, Split, Watch, Copied (quoting `duplication.min_tokens`), Untested, Changes (quoting the churn window), Limits (the five ceilings, "Fitted from well-regarded Go modules." for Go) and Hard to follow.

**Markdown.** `report --format md` renders the repository report as Markdown (`internal/narrate/markdown`, which imports `narrate` and the standard library only): the headline as a heading, the lead, "Start here" (the first three hotspots with their band, rebuild time, changes, story and what to do) and a table of the ten packages with the most rebuild days (band, days, lines with `*` when over the size ceiling, copied share, untested exports, changes); with `--base` the change block comes first. The change block is a heading `## astimate: <verdict> — <F> of <N> changed packages need attention` (or the clean or empty forms), one table row per finding (package, what moved, `base → head` with `new` for a package without a base, `file:line` to open), then the heads-ups by rule with the passed count and `Copies between packages <base> → <head>`, and, when asked, a pointer to the HTML report. Table cells are escaped; the module row shows as `<module>`.

**In CI.** The action (`action/action.yml`) takes `html: true` to run `astimate report --base <base> --format html --out astimate-report.html` and upload it as the `astimate-report` artifact, and `comment: true` to post the `check --format md` text on a pull request, led by the hidden marker `<!-- astimate-report -->`: the comment is found again by the marker in the pull request's comments and updated in place, so a pull request never carries two. It needs `pull-requests: write`; with a missing token, a pull request from a fork or any API failure the step only warns, and it does not post when listing the comments failed, so as never to post twice.

## 11. Calibration

Two calibrations, in priority order.

### 11.1 Thresholds from a reference corpus (primary)

1. Assemble a corpus of 20 or more well-regarded Go modules: the standard library plus widely used, actively maintained open-source modules with permissive licenses.
2. Run the collector under `calibration/collect` over each (it calls the engine directly and writes every package's raw metrics, which `rank --json` does not carry) and pool all packages.
3. Set each capacity rule's `max`, and each density rule's `max` where the rule has one, at the pooled 90th percentile (nearest rank), rounded to two significant figures and then to the nearest readable step: 500 above 1000, 50 above 100, 5 above 10, otherwise 1 (0.5 for a percentage); a capacity `max` is at least one step. Set each density rule's `max_delta` at a quarter of the interquartile range (p75 minus p25), rounded up to a whole step, at least 1 for a count and 0.5 for a percentage, except that a rule whose default `max_delta` is 0 keeps it: zero tolerance on new duplicate blocks, untested exports, globals, init functions and nesting is a policy, not a statistic. `internal_imports` is pooled from cloned-module rows only, since the standard library is loaded as one module. `changed_func_cognitive_max` is a diff against a baseline, so it is fitted per function: every function of every row (the collector's `func_cognitive` counts) is counted as new, and its `max` is the pooled 99th percentile, rounded the same way. A module-wide metric (`dup_blocks_cross_pkg`) is pooled from the module rows only, one per cloned module, which the collector writes to `modules.jsonl`; the per-package counts on package rows are not used. Each other language is calibrated the same way from its own corpus (`calibration/corpus-<language>.yaml`), and `calibration/fit --language <id>` writes the result as that language's `languages.<id>` override, with one rule per rule the data fitted a statistic for. The rebuild parameters are not overridden. Kinds, `warn_at`, `over_max_delta`, `ratchet_from_zero`, `when` guards, requirements and rebuild parameters are unchanged by the fit; `over_max_delta` is fitted by the gate validation (11.4). `calibration/fit` applies these rules and records the distribution in `calibration/reports/`. The 2026-09-28 fit counted duplicate blocks at `duplication.min_tokens` 40; the default has counted them at 60 since 2026-10-14, and the corpus was not collected again (its 36 modules need cloning). A longer minimum only lowers both duplication metrics, so the `max` of `duplication_pct` (40) and of `dup_blocks_cross_pkg` (450) is looser at 60 than at 40, never stricter; the gate validation swept their `max_delta` and `floor` on the 60-token replays instead (`calibration/reports/thresholds-2026-10-14.md`).
4. Ship as `config_version: thresholds-<date>`. Good code passes by construction; the gate flags what falls outside what good projects do.
5. Re-run yearly or when the metric set changes.

### 11.2 Rebuild parameters from rebuild experiments (secondary)

The estimate's parameters are measured by doing the thing it estimates. For each of 30 or more packages across the reference corpus:

1. Delete the non-test implementation, keeping test files and exported signatures as stubs.
   The experiments are defined in `calibration/rebuild/rebuild.yaml`, generated by `go run ./calibration/rebuild select` and validated by its Go types. Each entry pins a cloned corpus module at its `corpus.yaml` commit and records the package's `RawMetrics` and pre-run estimate, a turn cap, and a hash of the stubbed tree. The stub strategy `signatures` replaces every function and method body in the package's non-test files, other than `init`'s, with `panic("not implemented")`, and removes the package initialization code that calls the package's own functions or methods: such a package-level variable keeps its type and loses its initializer, and such a top-level `init` statement is deleted. Everything else is kept, and imports that are no longer used are dropped. The oracle, run from the module root with `CGO_ENABLED=0 GOTOOLCHAIN=local GOWORK=off`, is `go test` of the package when it has tests, else of its in-module importers that have tests, followed by `go build ./...`. Selection: cloned-module packages without cgo or generated files, with at most 10 agent passes, split into six strata by tier and `has_tests` and sorted by `rebuild_tokens`. Seven slots per stratum start at evenly spaced positions, and each takes the first candidate that verifies at its pin (oracle passes before stubbing; the stub is deterministic and builds; the oracle's tests start on the stub and fail on its panic), with at most three packages per module. The standard library is excluded from the first selection. `calibration/rebuild/rebuild-trees.yaml` (`unit: tree`) defines 12 to 16 tree experiments, each a directory's package stubbed together with every non-main package below it. The oracle is the tree's own tests, or its importers' tests. The pre-run estimate is the members' `rebuild_tokens` summed and passed through the 7.2 curve once (`estimate_method: sum`), with each member's metrics and estimate recorded. The fit takes one unit at a time.
2. Have the target agent (Claude Code first) reimplement until the package's tests pass, with a turn cap.
   `go run ./calibration/rebuild run` runs each experiment `--repeats` times (default 3), each run in a fresh clone at the pin with the stub applied and hash-checked. The agent is Claude Code in print mode (`claude -p`, stream-json output, `--max-turns` at the experiment's `turn_cap`, a fixed prompt, tools limited to reading and editing files and the go commands, a pinned `--model`), started with the module root as working directory and a wall-clock timeout; another agent can be given as a command template. The runner never starts Claude Code without `--live`.
3. Record tokens, turns, wall time, whether tests passed, and whether importers still compile.
   Each run appends one row to `runs.jsonl`: the experiment and run index, the agent command and model, the pre-run estimate (`agent_passes`, `rebuild_tokens`, `human_days`, tier), the `RawMetrics`, `config_version` and `go_version`, the measured input, output and cache tokens, cost, turns, tool calls, wall time, session id and whether the turn cap was hit (null when the agent does not report one), whether the oracle's tests passed and whether `go build ./...` still compiles, whether the agent changed test files or other packages, and timestamps. `run.json` records the environment and totals. A rerun skips the (package, run) pairs whose oracle completed.
4. Regress the outcomes on the section 7.1 inputs and fit `context_budget`, the per-item token costs and the superlinear exponent.
   `calibration/rebuild/fit` takes each package's median measured tokens over its passing runs, where tokens are the session footprint: input + cache writes + output. It fits the 7.2 form, measured = overhead + scale × B × passes(`rebuild_tokens`/B), by nonlinear least squares, with the per-session overhead and the scale as terms outside the configuration and heteroscedasticity-consistent (HC3) standard errors. B is held and refitted at other budgets; the exponent is fitted from packages past the knee (at least three at r ≥ 1.1). Failed runs are censored and reported, and a negative fitted cost is clamped to 0 with a note. On 2026-09-28, 85 runs of 31 packages (three runs each, model claude-opus-5-5), 79 passing and 6 failed and censored, gave: overhead 8,399 ± 5,589, scale 7.63 ± 1.50 measured tokens per estimate token, `tokens_per_export` −169 ± 69 (clamped to 0), `tokens_per_untested_export` 304.5 ± 99.9 (300), `tokens_per_hidden_state` −357 ± 170 (clamped to 0), `superlinear_exponent` −0.008 ± 0.31, clamped to 1; the 14 whole-tree runs also clamp the exponent to 1 (0.96 ± 0.89). B = 37,500 fitted best of the budgets tried (R² 0.925, against 0.910 at 28,125 and 0.714 at 56,250); the form explains 92.5% of the variance in measured tokens. No input has a measurable token contribution beyond the form: volume, spec, `cognitive_total` and `func_count` predict passing only, and `exported_symbols`, `untested_exports`, `globals` + `init_funcs`, `test_funcs`, `cognitive_p90`, `max_nesting` and `fan_in` show nothing. Fitted freely, a test token costs 5.96 volume tokens (95% interval −77.6 to 89.5), so the data cannot tell whether tests are cost or help, and 7.2 keeps them at 1. Five of the six failed runs had already spent more than the predicted cost of a pass. The one-run first fit (25,000 / 120 / 2.79) is superseded.
5. Ship as `config_version: rebuild-<date>-<agent>` and flip `calibrated` to true for the estimate. Shipped as `rebuild-2026-09-28-claude-code-opus` from the three-run refit (report `calibration/reports/rebuild-2026-09-28-claude-code-opus.md`; the tree unit's report is `rebuild-trees-2026-09-28-claude-code-opus.md`).

This is well-defined and repeatable, unlike a refactoring-task corpus, and it directly measures what the number claims. It does not affect the gate.

### 11.3 Gate replay

`go run ./calibration/replay` measures the gate on real changes. It walks a revision range along first parents, checks each commit out into a temporary worktree and runs the engine's check against the first parent as the git baseline, as `astimate check --base <parent>` would, under a given configuration with exemption expiry judged at the committer date. A root commit, or a parent without the module, is judged against an empty baseline. It writes one row per checked package and module row to `packages.jsonl` with the findings (each with its `also` list, 8.1) and the full head and baseline metrics (every section 6 field: rows replayed before a field existed lack it, so `cyclomatic_total` and `cyclomatic_p90` are present from the first replay after 2026-10-14 on) and, since 2026-10-13, the changed functions over cognitive complexity 20 with their head and parent complexity (`changed_functions`; null without a function-level diff), so `changed_func_cognitive_max` can be re-evaluated per function, and, since 2026-10-14, each head row's `churn_commits` and `churn_authors` read from that commit's own history (6.6; null on the module row and the baseline), and, on the module row the cross-package blocks the commit may have added (`cross_added`): one entry per set of packages, as the rule of 8.1 matches them (each package a rename joined read as its group), on which some floor adds a block, with the token lengths of the parent's blocks on that set (`base`) and the commit's blocks on it that are neither exempt nor moved (`blocks`, each with its length in tokens, its kind, the packages it touches and each occurrence's package, file and first and last line), so `dup_blocks_cross_pkg` can be re-derived at any `duplication.min_tokens_cross` at or above the replay's `min_tokens`; an empty list when no set gained a block, absent on package rows and where the gate judged the full count (an empty baseline, a baseline without blocks); one row per commit to `commits.jsonl` with its author, trailers, changed files and packages and whether the module loaded, and `run.json`. A commit whose module does not load, or whose check selected a package that does not load (6.5), is recorded as not loaded with its error, and skipped; the commit row's `packages_failed` names each such package, and for a package that fails to extract in a checked commit, the package and the error with the worktree's path scrubbed. The worktree is added with no hooks run (`core.hooksPath=/dev/null`). Reruns resume by commit hash. The replay is package `internal/replay`: the calibration command keeps its flags, the default output directory under `calibration/data`, the go environment for cloned modules and a per-run build cache (`internal/gocache`, which `astimate dryrun` uses too), and `astimate dryrun` (9) runs the same replay over the last commits of the user's own repository. Labels join the rows on the commit hash, and the gate validation re-evaluates any rule at any threshold from these rows. Labels live in `calibration/replay/labels/<name>.yaml`, one entry per replayed commit (`verdict: block | allow`, `reason`, optional `metrics`, `provenance: proposed | confirmed | rule`), read and validated by package `calibration/replay/labels`. `calibration/corpus-commits.yaml` pins public repositories with agent-authored commits, identified by Co-Authored-By trailer or author; their histories are replayed and labeled by rule with `go run ./calibration/replay/label`: `block` when a later commit reverts the commit, or when one of the next 20 first-parent commits whose subject starts with fix or revert changes a Go function the commit changed; `allow` otherwise. The rule is objective and weak: a fix may be unrelated, and an unfixed bad change reads as `allow`. A fix-up measures defects, which the gate does not claim to catch, so the same command with `--rule split-extract` writes a second labels file per replay, `<name>-split-extract.yaml`, by the definition the gate does claim, read from the replay's rows alone with the capacity rules of the configuration the replay gated with: `block` when a later commit of the rest of the range (no window: a split lands far later than a fix) (a) splits a package the commit took over a capacity `max`, or grew by 100 or more SLOC while over one, by lowering that package's `sloc` by at least 25% (deleting it counts) while the module's total `sloc` falls by less than 5%, or (b) changes a file of a package whose `dup_blocks` the commit raised (for the module row's `dup_blocks_cross_pkg`, of a package the commit changed) and lowers that count by at least what the commit added while the package's `sloc` (the module's total, for the module row) falls by less than 25%; `allow` otherwise. The module's total is the sum of every package the rows show, each carried from its nearest row, so a package no replayed commit changed is missing from it. Evidence names the part (`split` or `extract`), the later commit and the package; each reason ends with the label's lookahead, the commits after it in the range, so the last commits of a range are censored. The split-or-extraction labels are the maintainability measure; the fix-up labels are kept as a second view of defects.

### 11.4 Gate validation

`go run ./calibration/validate --corpus <name>=<replay dir>:<labels file>[,<second labels file>] ...` measures the gate against the labeled replays of 11.3. It joins each replay's `packages.jsonl` and `commits.jsonl` with its labels file on the full commit hash, leaves out commits the replay did not load, and by default drops labels with `agent: false`, so the numbers describe agent-authored changes. A package row the replay marked `"baseline": "unavailable"` (beside `"new": true`) existed at the parent but failed to load there, so no rule ratcheted it from zero (8.1); the replay records the state so a validation can set those packages aside rather than score a ratchet the gate never applied, and `validate` does: such a row is dropped with the violations recorded on it, the commit's verdict is that of its other rows, and the Method says how many rows and violations were set aside. On a module row that records `cross_added` (11.3), `dup_blocks_cross_pkg` is re-evaluated as the gate judges it, the parent's count plus the blocks added of at least `--config`'s `duplication.min_tokens_cross` tokens, so the recheck reproduces the recorded verdicts; a module row without it is judged on its full count, which overstates the rule below the replay's floor. A commit fails when any of its package rows or its module row has a violation, as the replay recorded it under the configuration it ran with, of a rule that fails: a rule `--config` marks `severity: warn` (8.1) never fails a commit, whatever severity the replay ran it at. A rule fired on a commit when one of its rows recorded its breach, as a violation or as a warning with severity `warn`, under its own metric or in the `also` list of the finding it was merged into (8.1); rows replayed before findings were merged have no `also` and are read as they stand. So a `warn` rule still has its own row, marked `(warn)`, with its precision and recall, and is left out of the gate's row and every gate column. `--config` names the configuration to measure. Rows replayed under the same `config_version` are read as recorded. Rows replayed under another configuration are accepted when it is committed as `calibration/thresholds/astimate-<version>.yaml` and measures as `--config` does (the same `chars_per_token`, duplication settings and exemptions, so the stored metrics are the ones `--config` would measure; `duplication.min_tokens_cross` may differ when the rows record `cross_added`, or the corpus has no module row, and the rules on `dup_blocks_cross_pkg` are then re-evaluated at `--config`'s floor, which is how a floor is measured) and has the same rules, in the same order, on the same metrics, kinds and languages: each rule whose limits differ is re-evaluated on every row it judges, as a sweep is (below), in place of the recorded breaches, the recheck leaves it out, and the report's Method names it; a rule on another metric of the same kind and language in a replayed rule's place, when no rule of `--config` gates the replayed metric, is re-evaluated the same way and the replayed metric's recorded breaches are ignored, so a `dup_blocks_code` rule is measured on rows a `dup_blocks` rule gated (8.2); a rule that differs only in severity is read as recorded, since a severity decides only whether a breach fails. Otherwise `validate` refuses the corpus and says which: the configuration cannot be read, it measures differently, or its rules differ. Two targets, from M8 (section 14): the gate fails at least 80% of the commits labeled `block` (recall) and at most 10% of those labeled `allow` (false-failure rate). The churn metrics (6.6) are not gated, so `validate` reads them only as a `--candidate` rule would: rows replayed before 2026-10-14 hold them null, and a candidate on them is measured on the rows that carry them.

The report gives recall and the false-failure rate per corpus, for the rule-labeled corpora pooled, and for all corpora pooled; per rule, how many `block` and `allow` commits it fired on, its precision and its recall. A hand label whose `block` verdict rests only on capacity rules (it names only capacity metrics and cites no fix-up or revert) reads the same sizes the capacity rules read, so every view that holds such labels is also reported with them set aside, and that view is the honest number. Fix-up rule labels (11.3) measure later-fixed changes, not maintainability; the split-or-extraction labels are the maintainability measure. A size-only rule, `sloc_delta` of any package above t, is swept over t and reported beside the rules, so the report shows what the metrics add over the size of the change. Each rule's `max`, `max_delta`, capacity `over_max_delta` (0, the shipped value, and 1, 2, 3, 5, 10, 20, 25, 50, 100, 150, 200, 300, 500, 1,000, 1,500, 2,000, 3,000 and 5,000 from a thousandth to half of the `max`), density `floor` (0, 1, 2, 3, 4, 5, 8, 10, 15, 20 and 30 below the `max`, the shipped value, and none; only on a rule that ships one) or `when` guard is swept by re-evaluating it with `internal/gate`'s `Evaluate` over the rows' stored head and baseline metrics, so the sweep applies the gate's own semantics, and the re-evaluation at the shipped limits must reproduce the recorded violations, except where the gate's semantics changed after the replay: a row replayed before the direction test of 8.1 that records `changed_func_cognitive_max` may have a recorded `cognitive_p90` violation the re-evaluation no longer finds, which the report counts as a mismatch (rows without `duplicated_lines` judge `duplication_pct` as before). `changed_func_cognitive_max` is re-evaluated per changed function, its `max` and an `over_max_delta` on the same grid, on the rows that record `changed_functions`, exactly at any `max` above 20; a row without them, every row replayed before 2026-10-13 included, is judged on its one stored value, so the rule's `over_max_delta` cannot be swept on it, and the report says so. A row is judged by the first rule on the metric whose `roles` (8.1) take the row's recorded `role`, a row replayed before roles existed being a `library`, so a rule for `main` packages only, such as the default's second `has_tests`, judges no such row. Every rule gets keep, retune or drop, judged on the pool with capacity-only labels set aside: a rule that fired on fewer than 10 commits is kept as too thin to judge; the budget for one rule is the whole gate's 10% false-failure target; a rule with no swept setting within it, or whose best setting within it fails less than 2 points more of `block` than of `allow` commits, is dropped; a rule over the budget as shipped is retuned to the setting within it that fails the most `block` commits, except that a capacity rule with an `over_max_delta` within it is retuned to the `over_max_delta` within it with the best J, the largest on a tie, since its violations are mostly growth past a ceiling passed earlier, which no retuned `max` prevents; the rest are kept, none made stricter while the gate is over its false-failure target. A section gives each rule's part in the gate: the commits it fired on and those no other failing rule fired on, so a rule that fails no `block` commit alone adds no recall, and the `allow` commits it fails alone are what dropping it or making it a `warn` rule would spare; the 2026-10-14 retune made four rules `warn` from it. When the hand labels mark the passed commits read as a sample (reason `sampled pass`) and those not read (`passed, outside the hand sample`), the headline says how many of each the scored commits hold, since recall counts only the `block` commits found among the commits read. The report also lists the `block` commits the gate missed.

A row's metrics decode into the section 6 fields, so a field a row predates reads as 0 (null for a v1 field): `cyclomatic_total` and `cyclomatic_p90` are 0 on every row replayed before 2026-10-14, and no rule or candidate judges them until one is measured on rows that carry them.

`--candidate <file>` names a second configuration whose top-level rules on metrics `--config` does not gate are measured as candidates, so a rule is measured before it ships; `calibration/candidates/` holds such configurations. The replays never gated a candidate, so it is re-evaluated with `Evaluate` on every row it would judge, of every language, at its own setting: its row in the per-rule tables, marked `(candidate)`, is that re-evaluation, the gate's row and every gate column leave it out, and the recheck skips it. It is swept and advised like any rule, its advice saying whether to add it, which Advised never does, and a section of its own gives every view's gate without it and with it added alone, under both label sets when there are two.

When every corpus names a second labels file, the report scores every view under both label sets side by side: the same commits (the first set decides which are set aside or dropped), each set's verdicts, with the gate's, the size-only rule's and the advised gate's recall and false-failure rate. The sweeps and recommendations use the first set. With the split-or-extraction labels of 11.3 as the second set, a `block` commit crossed a capacity `max`, grew a package over one or raised a duplicate-block count, which the capacity and `dup_blocks` rules read, so recall under that set is near 100% by construction and its false-failure rate is the number that measures the gate.

The report for 2026-09-28 is `calibration/reports/gate-validation-2026-09-28.md`; `calibration/reports/gate-validation-2026-09-29.md` adds the split-or-extraction labels as the second set (`calibration/notes/split-extract-labels-2026-09-29.md`) and the `over_max_delta` sweep that fitted the capacity ratchets of 8.2. The 2026-09-28 corpora were not replayed again: their repositories need clones. - **CI:** `astimate check --format github` in a workflow step; exit 3 fails the job. This repository gates itself: the `selfcheck` job in `ci.yml` runs `action/` with `version: source` on pull requests (changed packages against `origin/<base>`) and on pushes to master (`--all` against the previous master tip), and `make check` runs `make selfcheck`.

## 13. Multi-language extension

The `Extractor` interface is the only language-specific surface. Adding a language means implementing it, defining module, package and internal import for that ecosystem, providing fixtures, and calibrating thresholds per language. Go keeps the native toolchain because `untested_exports` and coupling need type information. Other languages use tree-sitter.

### 13.1 TypeScript

TypeScript is parsed with `github.com/odvcencio/gotreesitter` (v0.55.1), a pure-Go tree-sitter runtime that bundles the TypeScript and TSX grammars. It needs no cgo, so `CGO_ENABLED=0` release builds keep working; the official cgo binding was not needed because the pure-Go runtime parses the fixture and the test snippets with no error nodes. The runtime is pre-1.0 and embeds all grammars by default; release builds pass the subset tags listed as `BUILD_TAGS` in the Makefile (one per grammar in use, checked against goreleaser and the action by a test) so only the two in use are embedded. The extractor lives in `internal/lang/typescript`; `internal/lang/duptok` is the duplicate finder over abstract token classes; the Go extractor uses it too, for both `dup_blocks` and `dup_blocks_cross_pkg`, with its `go/scanner` tokens mapped to the same classes.

Counting rules, the TypeScript counterpart of 6.5 (`testdata/ts/fixture/golden/COUNTING.md` shows each applied):

- **Module:** the directory of the nearest `package.json`; a directory below it with its own `package.json` is a separate module. There is no module path; package ids are directories relative to the root (`.` for the root).
- **Package:** a directory with at least one `.ts`, `.tsx`, `.mts` or `.cts` file that is neither a declaration file (`.d.ts`, `.d.mts`, `.d.cts`) nor a test file. `node_modules`, `dist`, `build` and dot-prefixed directories are skipped. Declaration files count nowhere. `.js` is not read.
- **Test files:** `*.test.*` or `*.spec.*` with extension `.ts`, `.tsx`, `.mts` or `.cts`, or anything under `__tests__/`, which belongs to the package containing that directory. A test file in a directory with no package is ignored. `test_funcs` counts calls to `it`, `test` or `bench` with a string or template first argument, at top level or inside `describe` bodies; member and curried forms such as `it.only` and `it.each(t)(...)` count once each.
- **Imports:** static `import` and `import type`, `export ... from`, `import x = require()`, and `require("lit")` or `import("lit")` calls. A relative specifier, a `paths` alias of the root `tsconfig.json` with its `extends` chain applied, or, with a `baseUrl`, a non-`node:` bare specifier resolves inside the module by the `tsc` rules (`moduleResolution` `bundler` where it and `node16` differ; exact alias match, then longest prefix, then the first target that resolves; JSONC accepted). A path resolves only to a file with a TypeScript source or declaration extension: for a `.ts`, `.d.ts` or `.js` specifier its `.ts`, `.tsx` or `.d.ts` form; for `.tsx` or `.jsx` its `.tsx`, `.ts` or `.d.ts` form; for `.mts`, `.d.mts` or `.mjs` its `.mts` or `.d.mts` form; for `.cts`, `.d.cts` or `.cjs` its `.cts` or `.d.cts` form; failing those, and for any other name, the name with `.ts`, `.tsx` or `.d.ts` appended (so `a.js` may resolve to `a.js.ts`). With `compilerOptions.resolveJsonModule` set (read through `extends` like `baseUrl`, the last file setting it winning), a specifier ending in `.json` also resolves to that file and counts by its directory like any other resolved file; JSON files add nothing to source metrics. With `compilerOptions.allowJs` set, or `checkJs` when `allowJs` is unset (each read through `extends` the same way), a lookup that finds no TypeScript file is retried for JavaScript, relative, alias and `baseUrl` lookups alike, after all TypeScript attempts as in tsc: a `.js` or `.jsx` specifier names that file or its `.jsx`/`.js` sibling, `.mjs` and `.cjs` the file itself, an extensionless one the name with `.js` or `.jsx` appended, and a directory its `package.json` `main` target, then `index.js` or `index.jsx`; the resolved file counts by its directory like any other, so a JavaScript-only directory counts nowhere, and JavaScript files add nothing to source metrics. Failing a file, a directory resolves through its `package.json` `typings`, `types` or `main` target, else its `index.ts`, `index.tsx` or `index.d.ts` (never an `.mts` or `.cts` index, as tsc resolves a directory as the extensionless name `index`); `.`, `..` and a trailing `/` are directories only. A relative specifier that resolves to nothing counts nowhere; a matched alias none of whose targets resolves, and a bare specifier that does not resolve under `baseUrl`, fall through to the built-in and npm rules. `node_modules` is not modelled, so a bare name that resolves under `baseUrl`, including under `allowJs` only to a local JavaScript file, is internal even where tsc would pick an installed typed package of that name (a deliberate difference). `extends` takes a string or an array of relative paths or bare names under `node_modules`; a bare package name uses its `package.json` `exports` (a string or a `"."` entry), then its `tsconfig` field, then its `tsconfig.json`; a leading `${configDir}` in `extends`, `baseUrl` or a `paths` target is the root configuration's directory (tsc 5.5); each of `baseUrl` and `paths` comes from the last file setting it, a child's `paths` replacing the parent's whole map, with relative values resolved against the declaring file; a missing file, a cycle or a chain deeper than 32 ends the chain. Such an import is internal only when the resolved file's directory is another package; an import of the same package is not counted, one landing in a non-package directory counts nowhere, and one leaving the module is external. Bare specifiers are external, counted by npm package name (`@scope/name` or the first segment). `stdlib_imports` counts Node built-ins by name without the `node:` prefix.
- **`exported_symbols`:** each name an `export` declaration adds (function, class, interface, type, enum, namespace, each bound `let`/`const`/`var` name), one per `export default`, and one per name in an `export {...}` list, including re-exports from other packages. Overload signatures and class members are not counted.
- **`untested_exports`:** exported functions, exported arrow or function constants, functions exported through a list, and public methods of exported classes; constructors, accessors, private, protected and `#` members are excluded. A candidate is untested when its name appears as no identifier in any test file of any package of the module, as in Go (6.4): the identifiers of every package's test files are collected once per module load into one index, so an export another package's test names is tested. A test file in a directory with no non-test source file, such as a top-level `test/`, `tests/` or `__tests__/` holding only `*.test.ts` or `*.spec.ts` files, is parsed like any other test file and its identifiers join the same index, but the directory is no package and reports no row. `has_tests` is true when the package has a test function of its own (`test_funcs > 0`) or when some candidate that is not excluded by the directive is named in that index; `test_files` and `test_funcs` stay the package's own, and a test file of no package adds nothing to `fan_in_tests`. This is name matching without type information. The closed interface list of 6.4 has no TypeScript analogue: without types a method cannot be shown to implement an interface the runtime calls, so no method is exempted that way. As in Go (6.4), a candidate whose doc comment (the comments directly above it, no blank line) has the line `//astimate:untested`, optionally followed by a space and a reason, is excluded and listed separately; a directive above a class does not apply to its methods. For an overloaded function or method, the directive applies when it is in the doc comment of any of its overload signatures or of the implementation, since TypeScript convention puts the doc comment on the first signature.
- **`globals`:** names bound by top-level `let` or `var` (not `const`), excluding `_`. A top-level `const` bound to an object or array is not counted, although its contents can be mutated: telling a mutated object from a read-only table needs the reference and data-flow analysis this extractor, without type information, does not run, and no measurement shows the case matters; it changes only with a measured reason. The Go exclusions of 6.5 have no TypeScript counterpart: `const` already covers sentinels and build information. **`init_funcs`:** the number of files with at least one top-level call statement, plain or awaited.
- **Functions:** top-level declarations, top-level variables initialised with a function or arrow function, and methods and function-valued fields of top-level classes; nested functions are scored inside their parent. The extractor lists these functions for `changed_func_cognitive_max` (6.5): the receiver is the class name for a method or function-valued field, empty otherwise; the fingerprint hashes the body's duplication tokens (identifiers ID, literals LIT, comments and zero-width tokens dropped) with token kinds hashed by name, semicolons left out so semicolon style does not mark a function changed, and the tokens of template substitutions included; a call to the function itself is kept distinct (a direct call by its bare name, or for a method `this.m(...)`, including from a nested arrow function but not from a nested function expression or class, which bind their own `this`, nor through `super` or another object); overload signatures have no body and are not listed.
- **Cognitive complexity** follows the gocognit rules: +1 plus nesting for `if`, `switch`, `for`, `for-in`, `for-of`, `while`, `do`, `catch` and the ternary; +1 flat for `else` and `else if`; +1 per run of like `&&`, `||` or `??` operators, with parentheses starting a new run; +1 for a labelled `break` or `continue`; nesting deepens inside nested functions; recursion is not counted. **Cyclomatic complexity** (6.5) counts 1 per function plus 1 for each `if` (an `else if` included), `for`, `for-in`, `for-of`, `while`, `do`, `case` (not `default`), `catch` and ternary, and for each `&&`, `||` and `??` operator, one per operator rather than per run (the logical assignments `&&=`, `||=` and `??=` and optional chaining add nothing, as in the cognitive walk); nested functions count in their parent. **`max_nesting`** counts `if`, the loops, `switch`, `try` and nested functions; an `else if` adds a level.
- **Duplication:** tokens are tree-sitter leaves with comments and zero-width tokens (automatic semicolons) dropped. Identifiers and `undefined` become ID; strings, templates, regexes, numbers, `true`, `false`, `null` and JSX text become one LIT each; a unary sign on a number is marked as a sign for the fold rule; type keywords such as `number` stay keywords. The literal-only, fold-sign and coverage rules are the Go ones (6.3).
- **v1 fields:** `instability`, `abstractness` (exported interfaces over exported classes, interfaces, type aliases and enums) and `main_sequence_distance` are computed, and `changed_func_cognitive_max` is computed by `check` from the function list above; the other v1 fields are null and the module row (8.1) is not produced; `generated_files` and `tokens_est_generated` are null because TypeScript has no generated-file header convention yet, so no file is left out of the size metrics. `--tokenizer o200k` is supported.
- Thresholds: the `typescript` override of section 8.2, fitted from the TypeScript corpus. The collector ranks each module root the corpus names and leaves out packages under test, fixture, example, benchmark and documentation directories.

Changed-package detection follows 8.4 with the TypeScript file rules stated there.

*Accepts when:* all four hold:

- Every bypass is visible: a finding is silenced only by an exemption that carries a reason and appears in the report.
