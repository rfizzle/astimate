# Churn: the cost of one history walk per run and per replayed commit

Date: 2026-10-14. Repository: astimate itself, HEAD `f40afe0` (299
first-parent commits), with the churn change built from the working tree.
Host: 13 cores, shared with another build and test run (load average 15 to
26 during the runs), Go build cache under a per-run `TMPDIR`, `GOPROXY=off`.

## Question

`churn_commits` and `churn_authors` (SPEC.md 6.6) are read with one
`git log --first-parent --name-only` over the window per operation, and
`dryrun` and the calibration replay read it once per replayed commit, from
that commit's own history. What does that add to a replay, at the default
window of 200 commits?

## Method

`astimate dryrun <worktree> --last 10 --out <dir>` run from a scratch
directory outside the repository, with `--config` the repository's own
`astimate.yaml` (`churn.commits: 200`) or a copy with `churn.commits: 0`,
alternating, three times each. No replay over any other repository.

The walk alone, at HEAD with the default window:

```
git -c core.quotePath=false log --first-parent --diff-merges=first-parent \
  --no-renames --relative --name-only --no-color --no-show-signature \
  --format=%x00%ae -n 200 HEAD --
```

takes 0.04 s and prints 92 KB.

## Results

| Run | `churn.commits` | Wall time |
| --- | --- | --- |
| 1 | 200 | 31 s (the command's own report) |
| 1 | 0 | 65.5 s |
| 2 | 200 | 35.9 s |
| 2 | 0 | 32.1 s |
| 3 | 200 | 33.4 s |
| 3 | 0 | 30.2 s |

The first churn-off run is an outlier (the host's load was at its peak);
over runs 2 and 3, churn on averages 34.6 s and churn off 31.2 s, a
difference of 3.4 s (11%) that is inside the spread between runs of the
same setting on this shared host. The walk itself accounts for about 0.4 s
over 10 commits (0.04 s each); attributing the touched files to packages
and reading the generated-file headers of the files still in the tree adds
no measurable time. The added cost is one `git log` per replayed commit,
as the design intends, and is small against the module load and the
baseline worktree each commit already pays.

Every one of the 28 package rows of the churn-on replays carries both
fields, each read from its commit's history: `internal/engine` counts 32,
31 and 30 at `0ca2b54`, `2a7522f` and `6c8d225`, oldest first, three
commits that touched it, since the 200-commit window slid past older
changes to it faster than these added; the 4 module rows
carry null, as the module row has no churn. The churn-off rows carry null
on every row.

## The highest-churn packages at HEAD

`astimate rank . --sort churn`, window 200 of 299 first-parent commits,
one author:

| Package | `churn_commits` | `churn_authors` |
| --- | --- | --- |
| `internal/metrics` | 34 | 1 |
| `internal/lang/golang` | 31 | 1 |
| `internal/engine` | 30 | 1 |
| `internal/report` | 25 | 1 |
| `internal/lang/typescript` | 24 | 1 |

`internal/lang/golang` and `internal/engine` are also the two packages
with the most rebuild passes here (1.1 and 1.4, `FEW_PASSES`), the pairing
`rank`'s `CHURN` column is meant to surface.

## Shallow clones

A shallow clone's oldest commit lists every tracked file as added, so
every package would read one commit by one author whatever the window.
The walk reports such a repository as having no history, and both metrics
are null there, as outside git. This covers the corpus clones of
`calibration/collect`, fetched at depth 1, whose rows therefore carry
null churn, and a CI checkout at the default depth.

## Decision

Churn ships on by default at 200 commits: reported, not gated, and no
change to the rebuild estimate or the tier. `churn.commits: 0` turns it
off for a run that wants none of the walk.
